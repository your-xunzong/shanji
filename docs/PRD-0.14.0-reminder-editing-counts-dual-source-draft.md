# 闪记 v0.14.0 强制提醒、快捷编辑、事项统计与双源更新 PRD 草案

> 状态：2026-11-04 用户确认；已进入实现与验证阶段，正式发布仍须通过发布门槛。

## 1. 背景

当前“强制”提醒虽然会保存事项的再次提醒间隔，但 Windows 原生持续通知、屏幕角落提醒窗和待确认提醒中心仍把“15 分钟后提醒”写死。用户在后台或单条事项中修改间隔后，这些入口的文案和点击结果仍可能保持 15 分钟，造成设置未生效的感受，并可能带来过于频繁的打扰。

事项卡目前只能通过卡片右侧的“编辑”按钮进入完整编辑，修改后还需要移动到保存按钮。对于频繁修正标题、备注、时间或分类的场景，操作距离过长。

事项侧栏目前只在“待处理”后显示当前列表长度。该数字随当前筛选变化，不是稳定的待处理总数；“今天、已逾期、已完成、回收站、全部事项”也没有各自统计。用户无法从导航直接判断各状态的工作量。

当前源码、标签、Release 和签名更新清单只发布到 GitHub；在部分网络环境中，用户检查或下载更新可能较慢。用户已创建公开 Gitee 仓库 `https://gitee.com/wu_-ji/shanji`，当前仓库为空，尚无分支、标签或 Release。

本版合并四项向后兼容改进：统一强制提醒间隔、增加双击编辑与 Enter 保存、为每个事项筛选显示可关闭的真实统计，并建立 GitHub/Gitee 双源发布与客户端择快更新。由于包含多项新增用户能力，按语义化版本规则发布为 `v0.14.0`，不再使用仅适合单项缺陷修复的 `v0.13.4`。

## 2. 目标

1. 后台可设置“强制提醒默认间隔”，支持常用值和 5–240 分钟自定义值。
2. 新建事项或重新选择“强制”方案时，自动采用当前后台默认间隔。
3. 单条事项仍可覆盖默认间隔；实际提醒频率以该事项保存的间隔为准。
4. 所有“稍后提醒”入口显示事项的实际间隔，例如“45 分钟后提醒”，点击后也确实延后 45 分钟。
5. 间隔修改后重新计算下一次提醒，不补发历史提醒，不制造重复通知。
6. 在非回收站事项的展示区域双击即可进入编辑，并把焦点放到事项内容。
7. 编辑时使用 Enter 快速保存，同时保护中文输入法组合态和备注换行。
8. 侧栏六种事项筛选分别显示自身真实数量，数字不再依赖当前打开的筛选。
9. 后台可控制是否显示事项数量；关闭后只隐藏六种事项统计，不影响提醒中心数量。
10. 每次正式发布把同一提交、标签、说明、安装包、更新包、签名和校验清单发布到 GitHub 与 Gitee。
11. 客户端并行检查两个官方源；同版本时选择响应更快的源，单源故障时自动使用另一个源。
12. 两个源的安装包必须是同一次构建产生的相同字节，不在 Gitee 重复编译或使用第二把签名密钥。
13. 双源选择不上传事项、备注、路径、设备标识或精确网络测速结果，且不进入快速记录、保存和提醒调度路径。

## 3. 范围

### 3.1 后台设置

- 将现有含糊的“默认提醒间隔”明确为“强制提醒默认间隔”。
- 提供 `15 分钟`、`30 分钟`、`60 分钟`、`2 小时`和“自定义”入口。
- 自定义值允许 5–240 分钟整数；保存前完成校验。
- 帮助文案：`新建或重新选择“强制”方案时使用；单条事项可以另外设置。`
- 设置保存成功后只影响新建事项、重新选择“强制”的事项，以及没有单独间隔的事项；不静默批量覆盖既有事项。

### 3.2 单条事项

- “强制”方案继续显示“再次提醒间隔”。
- 从其他方案切换为“强制”时，自动填入当前后台默认值。
- 用户单独修改后，保存该事项自己的间隔，不随以后后台默认值变化。
- 如果用户恢复提醒方案默认，间隔也恢复为当时最新的后台默认值。

### 3.3 提醒与稍后处理

以下入口统一读取事项实际间隔 `X`：

- Windows 原生持续通知：按钮显示 `X 分钟后`；点击后把下一次提醒安排到当前时间加 X 分钟。
- 屏幕角落提醒窗：按钮显示 `X 分钟后提醒`。
- 待确认提醒中心：按钮显示 `X 分钟后提醒`。

当 X 为 60、120 等整小时时，仍统一显示分钟，例如 `60 分钟后`，避免通知按钮与后台数值出现不同换算口径。

自动再次提醒和用户点击“稍后提醒”均使用同一事项间隔；完成、暂停或取消强制方案后不再继续提醒。

### 3.4 双击快速编辑与键盘保存

- 双击事项卡的内容展示区域进入现有完整编辑器，并把焦点放到“事项内容”输入框；保留现有“编辑”按钮，满足触屏、键盘和不熟悉双击的用户。
- 双击完成按钮、操作按钮、链接、输入框、选择框等可交互控件时，不进入编辑，避免一次操作触发两种结果。
- 回收站事项不能直接编辑，仍需先恢复；加载中或正在保存的事项不重复打开编辑器。
- 编辑器打开后：
  - 在事项内容、日期时间、数字等单行输入控件中按 Enter 保存全部修改；
  - 在备注中按 Enter 保存，按 Shift+Enter 插入换行；
  - 在下拉选择器展开或中文输入法仍在组合候选时，Enter 只完成当前选择或候选，不触发保存；
  - 按 Esc 取消本次编辑并恢复展示状态，不提交草稿。
- 保存期间禁用重复提交；成功后关闭编辑器并保留键盘焦点在该事项卡上。
- 保存失败时编辑器保持打开，所有草稿原样保留，显示：`修改没有保存，事项仍保持原样。请重试。`

### 3.5 每种事项的独立统计

- 侧栏固定为以下口径，统计之间允许业务上重叠：

| 导航项 | 统计口径 |
| --- | --- |
| 待处理 | 所有 `OPEN` 且不在回收站的事项，包括今天和已逾期 |
| 今天 | `OPEN` 且到期本地日期为今天的事项；今天已经逾期的事项同时计入“今天”和“已逾期” |
| 已逾期 | `OPEN` 且到期时间早于当前时间的事项 |
| 已完成 | 所有 `DONE` 事项 |
| 回收站 | 所有 `DELETED` 事项 |
| 全部事项 | 所有不在回收站的 `OPEN` 与 `DONE` 事项 |

- 每个导航项右侧都显示数字，包括 `0`；徽标固定右对齐，不能挤压或改变导航文字位置。
- 数量由数据层一次性聚合读取，不为六种分类分别加载完整事项正文。
- 创建、编辑到期时间、完成/恢复、删除/恢复、永久删除、仓库归并和日期跨越后刷新统计。
- 数量只表达当前数据事实，不作为提醒数量、未读数量或角标优先级。
- 无障碍名称包含分类和数量，例如 `已逾期，3 条`；高对比度和强制颜色模式不能只靠底色表达数字。

### 3.6 后台统计开关

- 后台设置新增开关：`显示事项数量`。
- 帮助文案：`在待处理、今天、已逾期、已完成、回收站和全部事项后显示当前数量。`
- 新安装和升级用户默认开启，以修复当前不完整的单一数字显示。
- 关闭后同时隐藏六个事项数量；“提醒中心”的待确认提醒数量保持显示，因为它属于提醒状态而不是事项筛选统计。
- 开关持久化到本地设置，不联网，不影响事项、提醒计划或筛选结果。

### 3.7 双仓源码与正式发布

- GitHub `https://github.com/your-xunzong/shanji` 保持规范事实源和唯一构建源；Gitee `https://gitee.com/wu_-ji/shanji` 是只读发布镜像，不接受独立发布提交。
- 首次启用时把完整 Git 历史、`main` 和现有标签同步到 Gitee；不回填历史 Release 附件，从 `v0.14.0` 开始镜像新的正式发行版。
- 版本只构建一次。GitHub Actions 生成三平台产物和签名后，Gitee 直接接收同一批文件，禁止在 Gitee 重新编译。
- 两个仓库同版本必须满足：
  - `main` 和 `vX.Y.Z` 标签解析到相同 Git commit SHA；
  - Release 标题、中文说明、正式/预发布状态一致；
  - 附件名称、字节大小、SHA-256 和更新签名一致；
  - `latest.json` 的版本、发布日期、说明和平台签名一致，仅下载 URL 主机不同。
- Gitee 访问凭据只保存为 GitHub Actions 加密 Secret，采用最小仓库权限；不得写入远端 URL、源码、日志、附件或应用配置。
- 发布流水线分为：构建并创建 GitHub 草稿 → 创建 Gitee 预发布镜像并验证 → 维护者确认 GitHub 正式发布 → 自动把 Gitee 改为正式版 → 双源只读复核。
- 任一源未完成标签、Release 或附件校验时，不得宣称“双源发布完成”；已成功的单源不回滚或删除，修复后幂等补齐另一个源。

### 3.8 双源更新发现与择快规则

- 客户端的更新检查仍须由用户授权；检查时并行请求：
  - GitHub 最新稳定版 `latest.json`；
  - Gitee 最新正式 Release API，再读取该 Release 的 `latest.json` 附件。
- 每个源独立记录从请求开始到取得有效清单的耗时，不使用持续测速、后台 ping 或大文件测速。
- 两个清单均有效时：
  1. 若版本不同，选择语义版本更高的稳定版；界面显示`两个发布源正在同步，本次使用较新的版本`。
  2. 若版本相同且当前平台签名一致，选择有效清单响应更快的源。
  3. 若版本相同但当前平台签名不一致，视为镜像不一致，优先使用 GitHub 规范源并显示`镜像仍在同步，本次使用 GitHub`；不得从不一致的 Gitee 清单下载。
- 仅一个清单有效时直接使用该源；另一个源的超时、404、限流、TLS 或格式错误不阻塞更新。
- 两个源都不可用时显示既有可恢复错误，当前版本和本机数据不变。
- 下载选中源失败时允许自动从另一个具有相同版本和签名的源重新开始一次；不得无限重试、拼接两个源的数据或绕过签名验证。
- 选择结果只在本次检查/下载会话中有效；下次检查重新并行测量，避免把一次网络状况永久固化。

### 3.9 更新安全与隐私边界

- 两个源的更新包继续使用同一长期 Minisign 私钥签名，客户端只内置同一公钥；任何源都不能关闭或降级签名验证。
- 客户端只接受精确主机和路径：
  - `github.com/your-xunzong/shanji/releases/download/`；
  - `gitee.com/wu_-ji/shanji/releases/download/`。
- URL 使用结构化解析校验 HTTPS、主机、仓库路径、版本标签和附件名，不使用宽泛字符串包含判断，不允许用户配置第三方更新源。
- 更新元数据和下载逻辑进入 Rust 适配器；共享领域逻辑不依赖 GitHub 或 Gitee，前端不直接下载或安装文件。
- 自动检查继续默认关闭。现有用户此前只授权 GitHub 网络访问，因此升级后首次自动检查前必须重新确认：`更新检查会同时连接 GitHub 和 Gitee，以选择更快的官方下载源。不会上传事项或本机路径。`
- 手动点击“检查更新”视为本次双源联网授权；拒绝或关闭授权时不访问任一源。
- 日志只记录去敏的源枚举、阶段、状态和整毫秒耗时区间，不包含事项内容、完整下载签名、访问令牌、查询参数或用户网络地址。

### 3.10 Gitee 附件容量与保留策略

- 发布前校验每个 Gitee 附件小于 100MB；超过限制时 Gitee 镜像任务失败，GitHub 正式产物不冒充或拆分为无法验证的文件。
- Gitee 镜像上传与 GitHub 相同的 11 类附件：三平台安装/便携包、三个更新签名、`latest.json` 与 `SHA256SUMS.txt`。
- 为给普通仓库附件总容量保留安全余量，Gitee 保留最近 5 个稳定版本的二进制附件；更旧版本保留源码、提交、标签和 Release 说明，历史安装包继续从 GitHub 获取。
- 清理只在新版本双源校验完成后进行，并在流水线日志中列出拟清理版本；不得删除最近 5 个稳定版本或 GitHub 附件。
- 若用户以后升级 Gitee 容量或改变保留策略，应通过显式发布配置调整，不在客户端远程下发。

### 3.11 更新界面

- 检查中显示：`正在连接 GitHub 与 Gitee 检查新版本…`，并继续说明不会上传事项、备注或本机路径。
- 找到更新后以一行弱化信息显示：`下载源：Gitee（本次响应更快）`或`下载源：GitHub（本次响应更快）`。
- 自动切换源时显示非阻塞状态：`当前下载源不可用，正在改用另一个官方下载源。`
- 不展示竞速动画、两列速度排行榜、精确公网延迟或“国内/海外”推断；源名称仅解释本次下载位置。
- “打开发布页”打开本次选中源对应版本的正式 Release；源尚未选定或镜像不一致时打开 GitHub 规范 Release。

### 3.12 兼容行为

- 既有事项已经保存的 15 分钟、30 分钟等间隔保持不变，不因升级被批量修改。
- 既有后台默认值保持不变；升级本身不主动改变提醒频率。
- 双击与 Enter 是现有编辑按钮和保存按钮的补充，原操作入口全部保留。
- “显示事项数量”需要一个布尔设置迁移，默认开启；迁移前创建可恢复备份，迁移失败不得启动到半更新状态。
- v0.13.3 及更早客户端仍只使用 GitHub，不受 Gitee 镜像影响；只有安装 v0.14.0 后才启用双源逻辑。
- 自动更新的授权状态需要版本化升级，不能把旧的“只访问 GitHub”授权静默扩大到 Gitee。

## 4. 非目标

- 不改变“重复、强调、一次性、自定义”方案的时间语义。
- 不新增按星期、时间段或次数递增的复杂策略。
- 不改变通知渠道开关、勿扰时段、邮件路由或完整通知内容开关。
- 不为快速录入增加必填项。
- 不批量重写已有事项的提醒间隔。
- 不把双击扩展到回收站直接编辑、时间画布拖拽编辑或批量编辑。
- 不移除现有“编辑”“保存修改”“取消”按钮。
- 不把事项统计解释为互斥分组，也不合并今天与已逾期的重叠数量。
- 不隐藏或复用提醒中心的待确认提醒数量。
- 不建立自有更新服务器、CDN、账号、遥测或持续网络测速服务。
- 不把 Gitee 设为独立开发主仓库，不允许两个仓库各自产生发布提交或二次构建。
- 不允许用户输入任意更新源，不支持预发布频道、降级安装或未签名包。
- 不保证永久保存所有 Gitee 历史二进制附件；GitHub 保留完整正式 Release 历史。

## 5. 失败与恢复

- 自定义值不是整数或不在 5–240 分钟内时，不保存设置，显示：`请输入 5–240 分钟之间的整数。`
- 设置持久化失败时保留用户输入，显示：`强制提醒间隔未保存，原设置仍然有效。请重试。`
- 单条事项保存失败时保留编辑内容和原事项，不修改下一次提醒。
- 双击进入编辑时若事项已被其他操作更新，保存前使用现有并发/更新时间校验；失败时保留草稿并提示重新核对，不静默覆盖。
- 统计读取失败时不阻塞事项列表；已有统计保持最后一次成功值，首次读取失败则暂时不显示徽标，并记录不含事项正文的诊断信息。
- 统计开关保存失败时保持原显示状态，提示：`事项数量设置未保存，原设置仍然有效。请重试。`
- 提醒动作读取不到事项间隔时，使用持久化后台默认值；后台设置也不可读时使用现有安全默认值 30 分钟，并记录不含事项正文的诊断信息。
- 系统通知发送失败时按既有降级路径进入标准通知、角落提醒窗或提醒中心，不改变下一次提醒时间。
- Gitee 发布失败时保留 GitHub 草稿/正式 Release 和全部构建产物，支持幂等重试；不得用旧版本附件补位。
- 两个仓库标签指向不同提交、同版本附件哈希不一致或签名不一致时，流水线必须失败并停止宣称双源完成。
- 双源检查中单源失败不向用户暴露 API、HTTP 状态码或内部 URL；仅说明已使用另一个官方下载源。
- 下载切源后再次失败时停止，保留当前程序和数据，提供“重新检查”和“打开发布页”。
- Gitee 单附件达到 100MB 门槛或总容量不足时，在发布检查中提前失败并给出维护者可执行的清理/减包提示，不把失败留到客户端。

## 6. 跨平台行为

- Windows：原生持续通知按钮动态显示 X 分钟，并以 X 执行稍后提醒。
- macOS：系统通知动作能力受系统限制；能显示动作时使用 X，不能显示时点击通知打开事项，角落提醒窗与提醒中心仍显示 X。
- Linux：通知服务对动作支持不一致；支持时使用 X，不支持时沿用打开事项的降级路径，角落提醒窗与提醒中心仍显示 X。
- 三个平台的调度和持久化规则一致，平台差异只存在于通知动作是否可见。
- 双击、Enter、Shift+Enter、Esc 和事项统计在 Windows、macOS、Linux 使用相同业务规则；macOS 的保存快捷键不要求 Command 键。
- 触屏或无法稳定产生双击的环境继续使用“编辑”按钮，不把双击作为唯一入口。
- Windows、macOS、Linux 使用同一双源选择规则和公钥；平台只选择各自支持的签名更新包。
- Linux AppImage 当前最接近 Gitee 单附件上限，发布流水线必须逐版检查；`.deb` 环境仍打开选中源的 Release 手动安装。
- macOS/Windows 应用内安装仍遵循现有签名、公证和安装模式，不因选择 Gitee 改变权限或安装流程。

## 7. 界面设计结论

### 第一轮：设计计划

- 具体用户：需要快速修正大量个人事项、掌握各状态数量、避免过密提醒，并希望在不同网络环境中稳定更新的个人用户。
- 页面唯一任务：事项页用于迅速定位并修改记录；后台设置只控制默认节奏与导航信息密度；更新页只回答“是否有新版本、从哪里安全下载、当前进行到哪一步”。
- 色彩 token：沿用现有设置页的背景、正文、弱化文字、边框和强调色，不为一个间隔设置新增装饰颜色。
- 字体 token：沿用应用现有正文、控件和数字字体；分钟数字使用现有等宽数字特性，避免切换数值时跳动。
- 布局 token：设置页保持单列字段节奏；事项卡继续原位展开编辑；侧栏数字使用固定最小宽度并与所有导航项共用同一右边线。
- 标志性元素：“可预判的结果反馈”贯穿两个场景——间隔旁实时预览通知按钮文字，侧栏每一行都在同一位置显示该筛选的事实数量。
- 更新页沿用现有“版本轨”，只在轨道下增加一条下载源说明，不创建双列仓库卡片。

```text
强制提醒默认间隔
[ 45 ] [分钟]          通知按钮将显示：45 分钟后
新建或重新选择“强制”方案时使用；单条事项可以另外设置。

○ 待处理                         73
⌁ 今天                            8
! 已逾期                          3
✓ 已完成                         26
× 回收站                          2
· 全部事项                       99

v0.13.3 ─────────────── v0.14.0
          下载源：Gitee（本次响应更快）
```

### 第二轮：自检与删减

- 不新增卡片、图标、渐变或动画，避免把一个频率设置包装成新的功能入口。
- 不同时展示下拉框和数字框；选择“自定义”后才出现数字输入，减少常态密度。
- 预览只解释最终通知文案，不重复帮助文字，也不展示内部字段名。
- 不给每个数量使用不同颜色，不增加统计卡或图表；数字是导航辅助信息，不是新的仪表盘。
- 不在卡片上增加“双击编辑”常驻说明；保留明确的编辑按钮，并只在首次需要时使用简短提示或可访问名称。
- Enter 保存不覆盖选择器和中文输入法自身的 Enter 语义；这是快速编辑可用性的硬边界。
- 双源信息不做成测速仪表盘；删除精确延迟、国别标签、胜负色和常驻状态，只保留本次实际下载源。
- 键盘焦点、错误信息、浅色、深色、高对比度、强制颜色和减少动态效果沿用现有设置页规则。

## 8. 验收标准

1. 后台把强制提醒默认间隔设为 45 分钟并保存，重新打开设置仍显示 45。
2. 新建事项并选择“强制”，事项编辑器自动显示 45 分钟。
3. 到期后自动下一次提醒安排在 45 分钟后，不是 15 分钟后。
4. Windows 原生持续通知显示“45 分钟后”；点击后数据库中的下一提醒时间约为当前时间加 45 分钟。
5. 屏幕角落提醒窗和待确认提醒中心均显示“45 分钟后提醒”，点击结果一致。
6. 单条事项改为 90 分钟后，其三个入口均显示并执行 90 分钟；其他强制事项仍使用各自间隔。
7. 后台默认从 45 改为 60 后，既有 90 分钟覆盖事项保持 90；新建或重新选择“强制”的事项采用 60。
8. 输入 4、241、小数、空值或非数字时不能保存，原设置和提醒计划保持安全。
9. 修改间隔、休眠恢复、应用重启和系统时间回拨后只计算一个下一提醒，不补发历史提醒或形成通知风暴。
10. 完成、暂停或取消强制方案后不再提醒。
11. “重复、强调、一次性、自定义”方案的既有行为和通知内容不变。
12. Windows、macOS、Linux 的支持状态及通知动作降级符合第 6 节。
13. 双击任一非回收站事项的非交互内容区域后，原位打开编辑器，事项内容输入框获得焦点。
14. 双击“完成”“删除”“暂停提醒”等按钮只执行按钮动作，不打开编辑器。
15. 修改标题后按 Enter，只保存一次并关闭编辑器；事项卡获得可见键盘焦点。
16. 备注中 Enter 保存，Shift+Enter 能插入换行；中文输入法候选确认的 Enter 不保存。
17. 编辑校验或保存失败时，编辑器保持打开，草稿和原事项均安全；Esc 取消时不提交修改。
18. 开启“显示事项数量”后，六个导航项始终显示数字，包含 0；切换当前筛选不改变其他分类数字。
19. 待处理、今天、已逾期、已完成、回收站、全部事项严格符合第 3.5 节口径；今天已逾期事项可同时计入今天和已逾期。
20. 创建、修改时间、完成/恢复、删除/恢复、永久删除和仓库归并后，统计及时刷新且不读取六遍完整事项列表。
21. 关闭统计开关后六个事项数字全部隐藏，提醒中心数量仍正常显示；重启后保持该选择。
22. 统计读取或设置保存失败不阻塞事项列表和编辑操作，也不显示错误统计为真实值。
23. 初次同步后，Gitee 的 `main`、所有既有标签和 Git 历史可读取；从 v0.14.0 起双源正式标签解析到同一 commit。
24. 同一版本在 GitHub/Gitee 的附件名称、大小、SHA-256 与 Minisign 签名一致；Gitee 不执行第二次构建。
25. 两源同时可用且返回同版本、同签名时，客户端选择清单响应耗时较低的源，并在更新页显示本次来源。
26. Gitee 更快时从 Gitee 下载；GitHub 更快时从 GitHub 下载；下一次检查重新测量而不是永久固定。
27. 任一源超时、404、限流、TLS 或格式失败时，另一个有效源仍能完成检查和下载。
28. 同版本签名不一致时不使用 Gitee；版本不一致时选择较高稳定版，并显示镜像同步状态。
29. 选中源下载失败后只自动切换一次，备用源必须是同版本、同签名；双源均失败时程序和数据不变。
30. 未重新确认双源联网授权的升级用户不会自动访问 Gitee；手动检查只发送更新所需请求，不上传事项或路径。
31. 发布时任何 Gitee 附件达到 100MB、总容量不足、标签不一致或附件校验失败，流水线失败且不宣称双源完成。
32. Gitee 只清理最近 5 个稳定版之前的二进制附件，源码、标签、说明和 GitHub 完整附件历史保留。
33. v0.13.3 旧客户端继续通过 GitHub 更新；v0.14.0 双源功能不破坏旧版升级路径。

## 9. 测试范围

- Rust 领域与数据层：5/15/45/60/240 分钟边界、设置回退、事项覆盖、重新计算、休眠/重启/时间回拨和提醒幂等。
- Windows 通知适配器：动态按钮文字与动作参数一致，不再出现固定 15。
- 前端：预设/自定义切换、校验、保存失败保留输入、强制方案采用默认、单条覆盖、恢复默认。
- 组件：系统通知映射、角落提醒窗和提醒中心都显示实际 X。
- 事项卡：双击目标过滤、自动聚焦、单次提交、Esc 取消、备注 Shift+Enter、IME `isComposing` 与保存失败保留草稿。
- 数据层：六种统计口径、今天/逾期重叠、零值、大数据量聚合、当地日期边界、完成/删除/恢复及事务一致性。
- 侧栏与设置：六个徽标、开关持久化、关闭后不查询或不渲染、提醒中心徽标不受影响、无障碍名称和键盘焦点。
- 发布流水线：空 Gitee 仓库初始化、完整历史/标签同步、单次构建双上传、预发布转正式、幂等重试、同 commit/哈希/签名校验、100MB 与容量门禁。
- Rust 更新适配器：并发超时、版本比较、同版本签名一致性、延迟选择、单源失败、一次下载切源、严格 URL allowlist 和取消行为。
- 更新 UI：双源授权、检查中、GitHub/Gitee 被选中、镜像同步中、自动切源、双源失败、手动下载与打开正确 Release。
- 安全：伪造版本、重定向到非白名单、同版本不同包、旧签名重放、Secret 脱敏和旧授权不扩大。
- 回归：快速录入、其他四种提醒方案、完成/暂停、设置保存、开机启动和通知降级。

## 10. 发布要求

- 版本：`0.14.0`。强制提醒包含缺陷修复；双击编辑、键盘保存和可控事项统计属于向后兼容的新功能，因此提升次版本。
- 同步更新 `docs/PRD.md`、`docs/DESIGN.md`、双源更新 ADR、验收文档、实现说明、四处应用版本及锁文件、`CHANGELOG.md` 和发布说明。
- GitHub Actions 配置最小权限的 Gitee Secret；正式运行前先用不含用户内容的测试标签验证源码推送、附件上传、预发布和清理权限。
- 完成适用的格式化、静态检查、前端测试、Rust 测试、版本一致性检查、三平台构建和双源发布演练后，才可创建 `v0.14.0` 正式标签与双源 Release。
- 发布完成后分别只读核对 GitHub/Gitee 的标签、目标提交、正式状态、附件名称/大小/哈希/签名和最新版本入口；全部通过前不得宣称双源发布完成。
