# 闪记（暂定名）产品需求文档

> 文档类型：PRD（Product Requirements Document；用户原始表述为 PDR）  
> 文档状态：v0.7.1 已实现并通过自动检查，真实安装包升级验收待完成；v0.8.0–v0.13.1 已完成代码与适用自动检查，待用户统一验收
> 更新日期：2026-09-08
> 目标平台：Windows、macOS、Linux 桌面端

## 1. 一页结论

闪记是一款离线优先、常驻后台的跨平台快速备忘工具。用户在任何应用中按下全局快捷键，立即获得焦点明确的输入框；按 `Enter` 保存后窗口自动隐藏，事项进入本地待办库并按系统时间提醒。

首版最重要的不是“功能多”，而是这条链路稳定且足够快：

`全局快捷键 → 输入一句话 → Enter → 已可靠保存`

产品遵循“紧急时刻，前台极简；日常管理，后台完整”的原则。快速录入只承担立即记下事项和提醒意图所必需的操作，非必要选项不得阻塞保存；类型、标签、排期、提醒方案、跟踪和数据管理由后台完整承接，后台复杂度不得进入紧急录入主链路。

建议 MVP 采用以下产品与技术边界：

- 默认快捷键使用可配置组合键，例如 `Ctrl/Cmd + Shift + Space`；“双击单个修饰键”列为增强功能，需分别验证各系统权限、误触和键盘兼容性。
- 未指定时间的事项，默认到期时间为当前工作日的“下班时间”；未完成时自动顺延到下一工作日的下班时间。
- 对当天必须完成的加班任务，用户可标记“今日必做”；到期后不自动顺延，而是在下班后继续按可配置间隔提醒，直至完成或明确暂停。
- 数据默认只保存在本机，不注册账号、不依赖网络；提醒、分类、搜索和导入导出均可离线工作。
- 推荐使用 Tauri 2 + Rust + TypeScript/Svelte + SQLite。Rust 负责数据、时间规则和调度，前端只负责显示与交互。
- “跨设备云同步”“AI 云端分类”“团队协作”不进入 MVP，避免显著增加体积、隐私风险和故障面。

## 2. 背景与问题

用户在工作中经常突然想到一个事项，但打开完整待办软件通常需要切换窗口、等待加载、选择清单、设置时间，记录成本高。结果可能是：

- 为了不打断当前工作而放弃记录；
- 临时写在聊天框、文本文件或纸上，之后无法统一管理；
- 只写内容、不设时间，事项长期沉底；
- 提醒工具与记录工具割裂，重复录入。

本产品通过全局快速入口和明确的默认截止规则，把“随手记”自动转为“会在合适时间再次出现的事项”。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 在用户不中断当前思路的前提下，2 秒内开始输入，5 秒内完成一次记录。
2. 每次提交都先可靠落盘，再关闭输入窗口，不因崩溃、休眠或重启丢失。
3. 未设时间的事项也有确定的下一次提醒时间，并能持续顺延直至完成。
4. Windows、macOS、Linux 的核心体验和数据语义一致。
5. 空闲时低资源占用、无需常驻云服务、支持便携迁移和可恢复备份。

### 3.2 非目标（MVP）

- 不替代完整项目管理、日历或团队协作软件。
- 不提供多人共享、评论、审批和权限体系。
- 不要求账号登录，不做自建云同步。
- 不读取用户所有键盘输入；只注册用户明确配置的全局快捷键。
- 不修改系统时间，也不自行充当 NTP 客户端；“同步系统时间”指以操作系统时间、时区及其变化为准。
- 不在首版承诺复杂自然语言理解的 100% 正确率。

## 4. 用户与核心场景

### 4.1 主要用户

- 经常在多个窗口间工作的个人用户：开发者、设计师、运营、管理者、学生等。
- 对启动速度、键盘效率、本地隐私和软件体积敏感的用户。

### 4.2 核心场景

1. 用户正在写代码，想起“下班前提交报销”，按快捷键输入并保存，不离开当前工作上下文。
2. 用户只输入“给供应商回电话”，未设置时间，系统默认安排到当天下班。
3. 到期后用户没有完成事项，系统在下一工作日自动顺延，并保留原始到期信息和顺延次数。
4. 用户打开管理窗口，将若干事项批量分类、加备注、修改时间或标记完成。
5. 电脑休眠或应用退出期间错过提醒，恢复后系统立即补发一次合并提醒，而不是连续轰炸。

## 5. 体验原则

- 快：唤起、聚焦、输入、提交均可只用键盘完成。
- 稳：保存成功是隐藏窗口的前置条件；任何失败都必须保留输入内容并可重试。
- 静：默认不过度提醒，不弹广告，不主动联网，不抢占不相关键盘输入。
- 清楚：自动推断的时间、分类和顺延结果必须可见、可改、可追溯。
- 一致：平台差异封装在底层，用户看到的事项状态与时间规则一致。

## 6. 关键业务定义

### 6.1 事项状态

| 状态 | 含义 | 是否继续提醒 |
| --- | --- | --- |
| `OPEN` | 待处理 | 是 |
| `DONE` | 已完成 | 否 |
| `ARCHIVED` | 已归档，不再出现在默认列表 | 否 |
| `DELETED` | 进入回收站，可恢复 | 否 |

“逾期”是由当前时间计算出的展示属性，不单独作为可写状态，避免状态与时间不一致。

### 6.2 工作日与下班时间

- 初始默认工作日：周一至周五。
- 初始建议下班时间：18:00，仅作为首次运行预设值，不得在业务逻辑中写死。
- 用户可在后台设置页修改工作日和默认到期时间；设置由 Rust 后端统一校验并持久化。
- 设置变更立即用于之后新建的无明确时间事项，以及之后发生的自动顺延。
- 已经生成明确到期时间的现有事项默认保持不变；如需同步修改，必须由用户主动选择“更新现有默认事项”并预览影响数量。
- 法定节假日识别不进入 MVP；未来可通过系统日历或节假日数据源扩展。
- 文中的“下一天”按产品语义解释为“下一工作日”。如用户关闭工作日功能，则按下一自然日计算。

### 6.3 未指定时间的默认到期规则

当用户提交事项但未明确指定日期或时间时：

1. 若当前时间早于本工作日下班时间，到期时间设为今天的下班时间。
2. 若当前时间等于或晚于今天下班时间，到期时间设为下一工作日的下班时间，避免创建一个立即逾期的事项。
3. 若今天不是工作日，到期时间设为下一工作日的下班时间。
4. 该时间的来源标记为 `DEFAULT_EOD`，界面显示“默认：今天 18:00”等提示；其中具体时间读取后台设置。

### 6.4 自动顺延规则

- 仅 `OPEN` 且到期来源为 `DEFAULT_EOD` 或已经自动顺延的事项参与自动顺延。
- 到期日结束后仍未完成，事项到期时间移动至下一工作日下班时间。
- 明确指定了时间的事项默认不自动顺延，只显示逾期；用户可单独开启“到期后每日顺延”。
- 标记为“今日必做”的事项不参与自动顺延，适用第 6.5 节的持续提醒规则。
- 每次顺延记录 `rollover_count`、原到期时间和变更时间，便于审计与后续统计。
- 自动顺延不能制造多份事项，也不能清除用户备注、分类或原始时间。

### 6.5 今日必做与加班提醒

- 用户可将事项显式标记为“今日必做”。系统可根据“今天必须完成”等文本给出建议，但未经用户确认不得自动启用持续提醒。
- 今日必做事项到达设定时间后仍为 `OPEN` 时，进入持续提醒状态；即使已过下班时间，也按后台配置的间隔继续提醒。
- 初始建议间隔为 30 分钟；用户可在后台设置 15 分钟、30 分钟、60 分钟或自定义间隔。自定义范围暂定为 5–240 分钟，避免高频通知风暴。
- 持续提醒直到用户标记完成、明确暂停提醒或将事项改为普通事项。仅关闭通知或关闭管理窗口不视为完成。
- “今日必做”无明确时间时始终归属创建当天：默认到期时间未过则当天到点提醒；默认时间已过则保存后立即提醒，不适用“下一工作日顺延”。
- 事项跨过午夜后仍保留原到期日并显示为“今日必做 · 已逾期”，不得静默改成第二天事项；持续提醒策略保持有效。
- 全局勿扰时段默认仍然生效。用户可对单个事项显式开启“允许在勿扰时段提醒”，但应用不能绕过操作系统级勿扰设置。
- “稍后提醒”只改变下一次提醒时间，不改变完成状态和原始到期时间。
- 每次重复提醒使用“事项 ID + 计划提醒时间 + 事项版本”生成幂等键，防止重启、休眠恢复或时间回拨造成重复轰炸。

### 6.6 时间与时区

- 调度以操作系统墙上时间为准，监听系统时区变化、休眠恢复和应用重启。
- 工作日默认到期时间属于“本地时间意图”；用户更换系统时区后，仍保持当地所配置时间的语义。
- 内部审计时间使用 UTC；需要表达“当地几点”的字段同时保留本地日期、时间和时区策略。
- 系统时间大幅回拨时不得重复发送同一提醒；提醒事件需要幂等标识。

#### 7.4.1 v0.1.1 系统级通知修复

- 系统级通知指由操作系统通知中心展示的原生横幅，不得使用应用置顶窗口模拟。
- Windows 安装版必须显示来源名称“闪记”和应用图标；窗口隐藏、程序驻留托盘时仍能通知。
- Windows 便携版首次启用通知时，应解释需要注册当前用户级 AppUserModelID；只有用户确认后才能写入对应系统配置，并提供可验证的撤销入口。
- 通知正文包含事项标题和到期信息；点击通知后显示主窗口。系统级专注模式、勿扰和通知总开关仍由操作系统控制，应用不得绕过。
- 提醒事件至少区分 `CLAIMED`、`SUBMITTED` 和 `FAILED`：`CLAIMED` 表示后台已原子领取，`SUBMITTED` 表示平台 API 接受提交，`FAILED` 保存去敏错误类别并进入有界重试。
- “10 秒后测试通知”必须走 SQLite、调度器、平台适配器完整链路。平台 API 返回失败时保留测试事项并显示恢复建议，不得报告测试成功。
- 平台 API 接受提交不等于用户必然看到横幅；若系统专注模式抑制横幅，应用应说明可在通知中心或系统设置中核对。

v0.1.1 验收要求：

1. Windows 安装版连续触发 20 次测试通知，无应用侧漏发和重复，来源名称及图标正确。
2. Windows 便携版在未注册时明确提示；授权注册后能发送原生横幅，撤销后移除自身通知身份。
3. 点击通知能唤起主窗口；应用窗口隐藏不影响通知。
4. 平台提交失败会记录 `FAILED` 并向用户显示可执行建议，不会提前写成成功。
5. macOS 检查并请求系统通知权限；Linux 在无通知服务时明确降级，不伪造成功状态。

### 7.5 后台运行、托盘与设置

### 7.5.1 v0.2.0 首次引导与开机启动

- 安装版首次启动时自动校验并准备原生通知身份；成功后明确显示“原生系统通知已就绪”。
- 便携版不得静默注册系统通知身份；引导中解释当前用户级注册的影响，只有用户点击启用后才注册，并保留撤销入口。
- 引导中的“开机启动”默认勾选，但在用户点击“完成设置”前不得修改系统。点击“跳过”不得启用开机启动或修改快捷键。
- v0.2.0 升级用户也显示一次该版引导；完成或跳过后持久化引导版本，后续启动不重复出现。后台设置提供“重新打开首次引导”。
- 开机启动入口使用 `--background` 参数，启动后驻留托盘且不抢占前台焦点。设置页每次打开时读取操作系统实际状态，不以 SQLite 缓存冒充系统状态。
- 开机启动变更失败时，界面恢复到实际状态并给出平台错误建议。便携版启用时提示移动或删除程序目录会使启动项失效。
- 快捷键保存前先做语义校验，再尝试系统注册；注册或数据库保存失败时恢复原快捷键。界面必须展示后端返回的字符串错误，不得统一降级为“设置没有保存”。

v0.2.0 验收要求：

1. 新安装和从 v0.1.1 升级均只显示一次引导；跳过、完成和设置页重新打开三条路径可用。
2. 引导默认勾选开机启动，但关闭引导或点击跳过不会写入系统；点击完成后系统实际状态与界面一致。
3. Windows 重启登录后闪记以后台模式运行且不显示主窗口；关闭开机启动后不再启动。
4. 安装版通知身份默认就绪；便携版未经授权不注册，授权与撤销均只影响便携版身份。
5. 空快捷键、只有修饰键、无法解析、被占用和系统注册失败均显示对应中文提示，原快捷键继续生效。
6. macOS 登录项和 Linux 自启动在受支持环境使用同一状态闭环；平台拒绝或桌面环境不支持时明确降级。

### 7.5.2 v0.2.1 启动初始化可靠性

- 主窗口和快速录入窗口必须在 Rust 托管状态、数据库、通知服务及调度器完成初始化后创建，页面不得观察到 Tauri 内部的 `state not managed` 错误。
- IPC 层对“托管状态尚未就绪”这一瞬时启动错误进行有限退避重试；数据库只读、输入错误等业务失败不得自动重试或被改写。
- 验收要求：冷启动和开机后台启动均无需手动点击“重试”；普通命令错误仍立即显示原始可执行提示。

### 7.5.3 v0.3.0 首次设置默认提醒时间

- 首次启动引导在“开机启动”和“快捷键”之间增加“默认提醒时间”步骤，用于设置未填写时间事项的默认提醒时刻。
- 新安装初始建议值为 `18:00`；引导必须显示当前持久化设置，并提供系统时间选择器以及 `17:30`、`18:00`、`18:30` 快捷选项。
- 用户点击“完成设置”后，默认提醒时间与该次引导的其他设置一起保存。点击“跳过”或关闭引导不得修改当前默认时间。
- v0.2.x 升级用户显示一次 v0.3.0 引导；从后台设置重新打开时继续显示当前已保存时间。
- 默认提醒时间变更只影响新事项和之后的自动顺延，提交时固定使用 `updateExistingDefaultItems = false`，不得修改已有事项的到期时间或提醒计划。
- 时间为空或格式无效时不得继续。保存失败时保留用户选择，并显示“默认提醒时间没有保存，原设置仍然有效，请重试。”
- Windows、macOS、Linux 使用同一领域校验和保存语义，不新增系统权限。

v0.3.0 验收要求：

1. 新安装及 v0.2.x 升级后，版本化引导中可以查看并修改当前默认提醒时间。
2. 未填写时间的新事项使用新设置；已有事项及明确指定时间的事项保持不变。
3. 点击“跳过”、按 `Esc` 或关闭重新打开的引导均不修改默认时间。
4. 空值和无效时间不能进入下一步；保存失败不丢失选择，原设置继续有效。
5. 后台设置与首次引导显示相同的默认时间，三平台行为一致。

### 7.5.4 v0.3.1 快速时间入口与升级数据保护

- 快速录入的时间入口必须是可见、可点击、可键盘操作的明确控件，不得使用透明输入框覆盖文字造成“按钮没有功能”的错觉。
- 点击时间入口后提供“使用默认时间”“今天下班”“明天下班”“指定日期时间”；选择后立即显示最终本地日期时间，并可一键恢复默认规则。
- 启动时在打开数据库前确定并记录实际数据目录；安装版固定使用系统应用数据目录，便携版仅在同目录存在 `portable.flag` 时使用程序旁 `data/`。
- 每次 schema 升级前必须使用 SQLite 一致性快照创建带 schema 版本的可恢复备份，备份完成后才允许迁移；迁移失败不得打开空库或覆盖原库。
- 如果目标数据目录为空，但已知旧目录或相邻便携目录存在非空数据库，不得静默创建新的空库；管理页显示“找到旧数据”，由用户预览来源、事项数量和修改时间后决定恢复。
- 管理页展示当前数据位置、事项数量、数据库更新时间及最近备份，并提供“立即备份”和“打开数据位置”。恢复属于高风险操作，必须再次确认且恢复前先备份当前库。
- 复制、备份和升级必须正确处理 SQLite WAL；不得只复制主数据库文件造成最近数据遗漏。

v0.3.1 验收要求：

1. 快速录入时间入口可用鼠标和键盘打开，选择、清除和再次打开均有明确反馈。
2. 安装版升级和覆盖安装后仍读取同一数据目录；便携版替换程序文件但保留 `data/` 后数据不变。
3. 从 v0.1–v0.3 的非空数据库升级前产生一致备份，迁移失败可以恢复原数据。
4. 发现旧数据库时不自动合并、不联网、不覆盖，只给出可验证的恢复入口。

### 7.6 类型、标签与事项操作（v0.4.0）

> 实施状态：v0.4.0 已完成 Windows 构建与从 schema v3 到 v4 的覆盖升级验证；macOS/Linux 的托盘交互与文件对话框仍需真实设备发布验证。
>
> 历史说明：本节记录 v0.4.0 当时的可编辑类型和“收件箱”语义。自 v0.6.0 起新增固定七种事件类型，“工作/个人”等旧类型仍保留为单选“类型”，“收件箱”不再作为用户可见类型；当前行为以第 7.9 节为准。

#### 7.6.1 类型与执行要求

- “类型”用于单选表达事项的工作性质，例如“工作”“个人”；现有 `categories` 数据在迁移后作为类型继续使用，事项关系保持不变。
- 用户可以新增、重命名、改色、排序和删除自定义类型。类型名称在有效类型中唯一，名称长度 1–30 个字符。
- 内置“收件箱”是无类型的展示兜底，不作为可删除数据库记录。
- 删除仍被事项使用的类型时，用户必须选择“改为无类型”或迁移到另一类型；任何选择都不得删除事项。
- 已记录事项可以随时修改类型，包括逾期事项；类型变化不得改变到期时间、完成状态和原文。
- “今日必做”是决定持续提醒方式的独立执行要求，不属于类型，不允许通过删除类型间接关闭提醒。

#### 7.6.2 标签

- 标签用于多选表达工作内容，一个事项可以没有标签或拥有多个标签。
- 用户可以新增、重命名、改色和删除标签；颜色从可访问调色板选择并在文字之外显示标签名称。
- 删除标签只解除它与事项的关联，不删除事项、不改变类型和提醒。
- 快速录入可以选择常用标签，管理页可编辑已有事项的全部标签。

#### 7.6.3 事项操作与回收站

- 事项卡片提供明确的“完成”“编辑”“删除”操作；完成后可以恢复。
- 删除为软删除，进入回收站并停止提醒；操作后短时间内提供撤销。
- 回收站默认保留 30 天，支持恢复。永久删除必须二次确认，并同时清理该事项的标签关系与提醒/审计记录。
- 事项编辑支持标题、备注、类型、标签、时间、今日必做与重复提醒间隔；一次保存应在同一事务中完成。

#### 7.6.4 Excel 报表

- 用户主动选择保存位置后导出本地 `.xlsx`，默认包含“事项明细”和“分类汇总”两个工作表。
- 明细至少包含：事项内容、备注、状态、类型、标签、创建时间、当前到期时间、完成时间、是否今日必做、顺延次数和提醒状态。
- 导出前可按时间范围、状态、类型和标签筛选；回收站默认不导出。
- 导出使用本地时间展示并在表头说明时区；任何以 `=`, `+`, `-`, `@` 开头的用户文本必须转义，避免 Excel 公式注入。
- 导出不修改数据库，不包含邮件凭据、内部错误或未提交草稿。成功后显示文件位置与记录条数，失败时不留下冒充成功的损坏文件。

#### 7.6.5 托盘交互

- Windows 与 macOS 双击系统托盘图标打开并聚焦管理窗口；单击仍遵循系统常规行为。
- Linux 的 Tauri 托盘事件并非所有桌面环境都支持；支持双击时使用相同行为，不支持时保留托盘菜单“打开闪记”作为明确降级。
- 本需求中的“双击任务栏”按跨平台可实现边界解释为“双击系统托盘图标”；操作系统管理的任务栏应用图标不作为自定义双击入口。

v0.4.0 验收要求：

1. 已有事项能在不改变时间的情况下修改类型与多个标签，重启后保持。
2. 类型/标签增删改均处理在用数据，任何删除操作不连带删除事项。
3. 完成、恢复、软删除、撤销和回收站恢复停止或恢复正确的提醒计划。
4. Excel 可由常见办公软件打开，列值与数据库一致，公式注入样例不会执行。
5. Windows 托盘双击稳定打开唯一主窗口；不支持双击的平台仍能从菜单打开。

### 7.7 持续可见提醒与通知渠道（v0.5.0）

> 实施状态：v0.5.0 已完成 Windows 构建及从 schema v4 到 v5 的覆盖升级验证；原生通知的系统级可见性可由设置页逐项测试，macOS/Linux 真实设备发布验证仍待完成。

#### 7.7.1 提醒展示与找回（不控制频率）

事项在什么时候再次提醒，只由第 7.9.5 节的事项提醒方案、事项自身间隔和安静时段决定。设置页这一组只管理提醒出现在哪里，以及用户从哪里找回可能错过的提醒；不得再提供一套全局重复频率与事项方案并行生效。

1. **标准系统通知**：使用操作系统原生横幅/通知中心，适合普通事项，默认开启。
2. **原生持续提醒**：Windows 使用 `Reminder` 场景并提供“完成”“15 分钟后”两个完整可见的快捷按钮；点击通知正文打开对应事项。满足系统条件时保持在屏幕上，直至用户操作或关闭。系统拒绝、勿扰或平台不支持时降级到标准通知并记录原因。
3. **应用置顶提醒窗**：由闪记管理的小型始终置顶窗口，显示事项、到期时间以及“完成”“稍后提醒”“打开”操作。默认关闭，用户主动启用；多条提醒排队显示，可拖动且不强制抢走当前输入焦点。
4. **待确认提醒中心**：管理页保存未完成且已经到期/已投递的事项，托盘菜单与设置入口显示数量，用户能直接打开所有可能错过的提醒。它是找回入口，不是提醒渠道或开关，不用创建测试事项来验证。

默认策略：普通事项只使用标准系统通知；“今日必做”或选择“强制”方案的事项可使用原生持续提醒，其再次提醒时间仍由事项方案决定；应用置顶提醒窗默认关闭。用户可以选择展示渠道，但渠道开关不得改变提醒计划。

旧版“普通事项未确认时重复提醒”全局设置不再展示或参与调度；数据库字段暂时只为旧数据兼容保留，保存新版设置时关闭旧值。普通、今日必做及其他事件都按各自已保存的提醒方案计算下一次提醒，不静默套用另一套全局间隔。

平台边界：

- Windows：实现标准通知、原生持续提醒、置顶提醒窗与通知操作。专注助手和系统通知总开关仍可能抑制通知。
- macOS：通知是否持续由用户在系统设置中选择“提醒”或“横幅”；应用提供设置引导，并以置顶提醒窗作为可选增强。
- Linux：优先请求 critical/不自动过期提示，但通知服务可以忽略过期策略；不可靠时提示用户启用置顶提醒窗，托盘事件按桌面环境降级。
- 任何平台都不能仅凭“平台 API 已接受”断言用户已经看到。只有用户点击完成、稍后提醒或明确确认，才记录为用户操作。

#### 7.7.2 邮件与按标签路由

- 通知渠道采用可扩展适配器：首个网络渠道实现 SMTP 邮件；后续渠道另行评审，不在本版本静默增加第三方服务。
- 邮件默认关闭。用户主动填写 SMTP 地址、端口、加密方式、发件人、收件人和用户名，并明确启用后才允许联网。
- 密码或授权码只保存到操作系统凭据存储，不写入 SQLite、日志、导出文件或版本库。
- 用户可配置“标签 → 渠道”路由，例如“客户”标签同时发送系统通知与邮件；无匹配标签时只执行默认本地渠道。
- 邮件默认只在首次到期时发送一次，重复系统提醒不重复发邮件；用户可以单独选择“今日必做每次重复也发邮件”，界面必须提示可能产生大量邮件。
- 每次渠道发送使用稳定幂等键并记录不含正文和凭据的投递状态；失败按有限退避重试，不阻塞本地保存和系统通知。
- 设置页提供连接测试和向自己发送测试邮件；失败时显示可执行建议，不能将“已排队”写成“已发送”。

验收要求：

1. 标准通知、原生持续提醒和置顶提醒窗可分别测试；测试按钮说明实际结果。待确认提醒中心提供直接打开动作和当前数量，不以新增测试事项代替入口。
2. Windows 原生持续提醒包含操作按钮；置顶窗不抢占正在输入的应用并能排队处理多事项。
3. 普通事项与今日必做分别按自身提醒方案运行；关闭展示渠道不改写频率，旧版全局重复值不再制造额外提醒。未完成的今日必做在下班、跨午夜、休眠恢复和重启后继续按已保存间隔提醒且不重复轰炸。
4. 提醒中心与托盘数量来自数据库事实状态，完成或暂停后及时消失。
5. SMTP 未启用时应用无新增网络请求；启用后密码只存在系统凭据存储，标签路由和发送幂等可验证。

### 7.8 已确认的版本实施顺序

1. `v0.3.1`：快速录入明确时间选择、数据目录可见、升级前一致备份与旧数据恢复入口。

### 7.9 七种事件与可组合提醒（v0.6.0）

> 确认状态：2026-09-01 已确认。固定七类为“普通、一次性、今日必做、预警、持续、月度、年度”；“重要”是可用于任意事件的独立标记。事项采用“事件类型—类型—标签”三层模型：事件类型表达时间性质，类型表达工作或生活性质，标签用于多选补充内容特征。

#### 7.9.1 目标与体验原则

- 紧急录入时，用户只需输入内容并按 `Enter` 即可可靠保存；选择事件类型、标签和高级提醒方案均为可选操作。
- 后台提供完整的事件转换、提醒排期、默认方案、标签、状态和历史管理，但不得增加快速录入的必填步骤。
- 事件类型负责表达生命周期和必要时间范围；提醒规则负责“什么时候再次出现”；通知强度负责“以何种方式出现”。三者不得用一个含糊字段互相覆盖。
- 已有事项升级后保持正文、备注、时间、状态、标签关系和已发送提醒记录，不因新默认值静默重算。

#### 7.9.2 七种固定事件

| 事件类型 | 默认行为 | 必要时间字段 |
| --- | --- | --- |
| 普通 | 每天在默认或指定时间提醒，直至完成或暂停 | 可选指定时间 |
| 一次性 | 只提醒一次；当地日期结束后不再提醒，事项和历史仍保留 | 默认或指定时间 |
| 今日必做 | 到期后按后台间隔持续提醒，跨下班和午夜仍不停止 | 到期时间、持续提醒间隔 |
| 预警 | 在目标发生前按提前量进入预警期，预警期内每天提醒 | 目标时间、提前量 |
| 持续 | 在开始至结束的闭区间内按选定周期生成提醒 | 开始时间、结束时间、周期 |
| 月度 | 按当地日历逐月生成周期，可完成本次或结束系列 | 每月日期和当地时间 |
| 年度 | 按当地日历逐年生成周期，可完成本次或结束系列 | 每年日期和当地时间 |

- “重要”是独立布尔标记，任何事件均可标记；它参与展示、筛选和通知强度预设，但不得静默改变事件时间。
- 月末没有指定日期时使用当月最后一天；年度事件选择 2 月 29 日时，非闰年使用 2 月最后一天，并在界面明确显示计算结果。
- 事件类型可以互相转换。目标类型缺少必需字段时，系统先要求补全并预览新的下一次提醒；补全失败或保存失败时原事件保持不变。

#### 7.9.3 事件类型、类型与标签的三层模型

| 维度 | 用户要回答的问题 | 规则 | 示例 |
| --- | --- | --- | --- |
| 事件类型 | 这件事在时间上如何发生？ | 固定七种，单选 | 今日必做、预警、年度 |
| 类型 | 这是什么性质的事？ | 用户自定义，最多单选一个 | 工作、个人、学习、健康 |
| 标签 | 这件事还有哪些内容特征？ | 用户自定义，彩色多选 | 项目 A、客户、报销、发布 |

- 类型不与某一事件类型绑定。例如“工作”可用于普通、今日必做、预警或年度事件；转换事件类型时原类型和标签继续保留。
- 类型可新增、重命名、改色、排序和删除。删除在用类型前，用户必须选择迁移到另一类型或保留为“未分类”；未分类是空值展示，不是系统内置类型。
- 标签可新增、重命名、改色、排序和删除。删除标签只解除关联，不删除事项。
- 类型和标签默认都不改变时间或提醒规则；未来若用于通知路由，必须由用户显式配置。
- 备注仍是独立的自由文本字段；标签是可重用、可筛选的结构化补充，不代替备注。

#### 7.9.4 不再显示“收件箱”

- 快速录入和管理界面不显示“收件箱”选项，也不把它作为第八种事件。
- 未选择事件类型的快速记录以内部“待选择事件类型”状态保存，仍出现在“全部事项”中；主界面使用简短横幅提示待处理数量，而不是建立新的导航分类。
- 新建的待选记录使用“重复”提醒，每天在默认或指定时间再次提醒，直到选择事件类型、完成、暂停或删除；这只是内部待处理状态，不作为第八种事件类型。
- 单条待选事件类型通知提供“设为普通”“选择其他事件类型”“稍后处理”。“设为普通”只处理当前记录，不改变将来记录的默认事件类型。
- 多条到期待分类提醒合并为一条数量通知，只提供“处理待选类型”和“稍后处理”，不得批量误设为普通。
- 选择类型、完成事项、暂停分类提醒或移入回收站后停止分类提示。选择类型时自动套用后台中该类型的默认提醒方案，并允许用户立即覆盖。

#### 7.9.5 提醒方案、频次与通知强度

界面提供五种提醒方案作为易懂预设，持久化层分别保存时间规则与通知强度，使类型和方案可以灵活组合：

| 方案 | 默认时间规则 | 默认通知强度 |
| --- | --- | --- |
| 重复 | 每天或按事件周期重复 | 标准 |
| 强调 | 逾期后按可配置间隔和每日次数重复，次日继续 | 强调 |
| 一次性 | 单次触发；当地日期结束后停止 | 标准 |
| 强制 | 保留所选频次，使用原生持续提醒或置顶提醒窗；关闭后按间隔再次出现 | 持续 |
| 自定义 | 组合提前量、周期、时间窗口、次数、渠道和逐级增强 | 用户选择 |

- 后台为七种事件分别保存默认提醒方案；默认值只影响新事件、主动选择该类型或主动点击“恢复默认”，不批量修改现有事项。
- 普通默认“重复”，一次性默认“一次性”，预警默认“预警期每天重复”，持续默认“按持续周期”，月度和年度默认“每个周期提醒一次”；今日必做默认方案由后台设置。
- 切换方案只重算未来提醒，不补发历史提醒；已发送提醒及用户操作历史保持不变。
- 普通的“重复提醒”是同一未完成事项每天再次提醒；月度、年度的周期是可分别完成的事件实例，两者在数据中不得混为一谈。
- 月度或年度事件选择“一次性”时，当前周期触发后自动排入下一周期并等待用户确认本次；选择重复、强调、强制或自定义时，当前周期按所选方案继续提醒，只有“完成本次”后才排入下一周期。

#### 7.9.6 预警、持续与周期计算

- 预警提前量内置“1 天、3 天、1 周、1 个月、1 年”，并支持自定义正整数和单位；从预警开始时间起每天在默认或指定时间提醒。到达目标时间发送正式提醒，之后由该事件的主提醒方案接管。
- 持续事件的周期内置“每天、每 3 天、每周、每月、每年”，并支持自定义正整数和单位。完成、暂停、删除或超过结束时间后不再生成提醒。
- 月、年按当地日历计算，不得换算成固定 30 天或 365 天；所有当地时间意图均保留时区策略，审计时间使用 UTC。
- 休眠、重启、时区变化或系统时间回拨后只计算下一次有效提醒；错过多个周期时最多补一条合并提醒，不连续补发历史触发点。

#### 7.9.7 编辑、状态和逾期边界

- `OPEN` 事件可修改类型、重要标记、标签和提醒方案；`DONE` 事件编辑后不自动恢复提醒，必须明确“重新打开”；`DELETED` 事件必须先恢复。
- 逾期事件原到期时间和已发生周期不可改写。转换类型需要未来时间时，创建新的未来计划并保留旧到期记录，界面使用“从现在开始新计划”说明影响。
- 完成、暂停、删除、转换和重新打开必须在事务中同时更新事项、未来计划与审计事件；任一写入失败则全部回滚。

#### 7.9.8 类型、标签与旧数据迁移

- 标签可新增、重命名、改色、排序和删除；一条事件可拥有多个标签。删除标签只解除关联，不删除事件。
- schema v5 升级前创建一致性备份。旧 `categories` 原样保留为“类型”，原事项的单选关系不变；旧 `tags` 和 `item_tags` 原样保留为标签及多选关系，不在两者之间复制或合并。
- 旧“今日必做”迁移为今日必做事件；其他已有类型的事项迁移为普通事件，但继续保留原类型；无类型事项的 `event_kind` 保持为空，进入“待选择事件类型”状态，其 `category_id` 仍可为空。
- 旧提醒计划保持原行为，不因普通事件的新默认“重复”而改变；新默认仅应用到新建、转换或主动恢复默认的事件。

#### 7.9.9 关于闪记

“设置 → 关于闪记”显示应用名称、从运行时读取的版本号、`© 2026 闪记`、离线与隐私说明、数据位置、打开数据位置操作以及第三方开源许可入口。不得写死一份可能与安装包不一致的版本号，也不得展示框架名、内部命令、数据库字段或调试信息。

#### 7.9.10 失败行为与跨平台降级

- 保存、转换或方案切换失败时保留原文和原计划，说明数据未被修改并提供重试；系统通知操作失败时保持待处理状态，用户可从提醒中心继续操作。
- Windows 原生持续通知支持分类操作；macOS/Linux 的通知按钮或持续性不可靠时，点击通知打开聚焦到对应事件的分类界面。强制方案无法持续显示时降级为应用置顶提醒窗和提醒中心。
- 系统勿扰、通知总开关和桌面环境仍可能抑制横幅；应用不得声称一定被用户看到，只有明确完成、稍后或确认操作才记录用户响应。
- 迁移失败不得继续打开空库或覆盖原库；未知枚举、损坏时间或不完整周期不得静默丢弃，应停止相关写入并提供恢复入口。

#### 7.9.11 非目标

- v0.6.0 不包含甘特图拖动编辑、云同步、账号、团队协作、手机端或新增第三方网络服务。
- 甘特图保持只读，支持日/周/月/年、今日线、类型和标签筛选以及点击打开详情；v0.11.0 起按第 7.14 节显示生命周期区间，不再沿用旧里程碑规则。

v0.6.0 验收要求：

1. 快速记录不显示收件箱，未选事件类型仍能一次提交并可靠落盘；失败时原文保留。
2. 单条待选类型通知能设为普通，多条通知正确合并；不支持通知操作的平台能打开应用内分类入口。
3. 七种事件可互相转换，缺少必要时间时给出可行动提示，转换失败不改变原事件，原类型和标签不变。
4. 普通默认每天提醒，一次性默认只提醒一次；类型默认方案可在后台设置且不静默修改旧事项。
5. 预警按提前量每天提醒，持续只在起止区间内按周期提醒，月度/年度按当地日历生成下一周期。
6. 方案切换只影响未来，不补发历史通知；完成、暂停、删除后不再提醒。
7. v5 的类型与标签分别原样保留，旧时间、提醒策略、正文和历史记录保持，迁移失败可恢复备份。
8. 关于页版本与安装包一致，版权、隐私、数据位置和许可入口可读且不暴露实现细节。
9. Windows、macOS、Linux 的不支持能力均按本节降级，核心事件与时间语义一致。

### 7.10 每日双时点重复提醒（v0.7.0）

> 实施状态：2026-09-01 已实现并验证。该能力是向后兼容的新功能，按语义化版本发布为 v0.7.0；后续需求按第 7.8 节拆分，避免形成单次过大的版本。

#### 7.10.1 目标

- 在不增加第六种提醒方案的前提下，扩展现有“重复”方案，使未完成事项默认可在每天两个固定时点提醒。
- 两个默认时点由用户在后台设置，快速录入不新增必填步骤；新事项直接使用已保存的默认值。
- 保留“指定一个时间后每天在该时间提醒”的既有行为，避免升级后静默增加旧事项或明确指定时间事项的提醒次数。

#### 7.10.2 产品规则

1. 后台“提醒设置”新增“重复提醒默认时间”，包含两个当地时间，初始建议值为 `10:00` 和 `17:00`。
2. 两个时间必须有效且不能相同；保存时按先后顺序显示。校验失败时保留输入，并明确提示哪个时间需要调整。
3. 首次引导沿用现有四步结构，在“时间”步骤中同时设置“未指定时间的默认提醒时间”和“重复方案每天两次的默认时间”，不额外增加引导步骤：
   - 新安装显示 `10:00`、`17:00` 两个重复提醒初始值，用户可以直接修改；
   - 从 v0.6.x 升级且尚未完成当前引导版本的用户显示持久化设置值；已完成旧引导的用户在 v0.7.0 首次启动时也只补显示一次新版引导，避免新默认设置不可发现；
   - 点击“完成设置”时，默认到期时间、两个重复时间、开机启动和快捷键作为一次用户操作提交；任一项失败不得把引导标为完成；
   - 点击“暂时跳过”、按 `Esc` 或从设置页重新打开后点击“关闭”，均不得修改三个时间或其他系统设置，但可将本次自动引导标为已处理；
   - 时间为空、格式无效或两个重复时间相同时不能继续，界面保留输入并指明需要调整的字段。
4. 新建或转换为“重复”方案时：
   - 用户没有指定时间：复制当时后台保存的两个默认时点，形成该事项自己的每日提醒计划。
   - 用户明确指定时间：仍按该指定时间每天提醒一次，不自动加入第二个时点。
   - 后台事项编辑器允许选择“使用两个默认时间”或“每天一个指定时间”；首版不提供三个及以上时点。
5. 后台或首次引导修改两个默认时间只影响之后新建、转换或主动点击“恢复默认时间”的事项，不静默重算已有事项。
6. 每天按当地日期寻找下一个尚未经过的时点：
   - 在第一个时点前创建，当天最多提醒两次；
   - 在两个时点之间创建，当天只提醒第二次；
   - 两个时点都已过去，当天不补发，下一次为次日第一个时点。
7. 休眠或应用退出期间错过多个时点时最多补发一条，随后直接排入下一个未来时点，不连续补发历史提醒。
8. 重复提醒持续到事项完成、暂停、删除，或月度/年度事件明确“完成本次”。一次性事件即使选择重复方案，也只在其有效当地日期内使用当天剩余时点。
9. 选择“重复”方案的其他事件沿用各自生命周期边界：预警只在预警期内、持续只在开始与结束之间、月度/年度只跟进当前周期；时间边界之外不生成提醒。
10. 每个时点继续使用稳定幂等键。系统时间回拨、重启、多开或设置保存重试不得让同一事项同一日期同一时点重复发送。
11. 通知渠道与现有规则保持一致：标准/持续/置顶提醒按事项设置投递；邮件仍默认只发送首次到期，除非用户已明确开启现有的重复邮件选项。

#### 7.10.3 数据与迁移

- SQLite schema 升级前创建一致备份；事项需要保存重复时间来源和一至两个当地时间意图，内存定时器仍不得成为事实来源。
- v0.6.x 已有“重复”事项迁移为“每天一个指定时间”，时间取其原 `due_local_time`，不得因升级自动增加第二次提醒。
- 新安装使用建议初始值；已有安装升级后只新增后台默认配置，旧事项、旧到期时间、提醒历史、类型和标签均保持不变。
- 当用户把事项切换到其他提醒方案时保留审计历史但停止使用每日时点；再次选择重复方案时明确选择使用当前默认值或原自定义值。

#### 7.10.4 失败行为与跨平台

- 默认时间保存失败时，原默认值继续有效；首次引导保留用户填写的三个时间并停留在当前步骤，事项保存失败时原提醒计划不变，界面说明“修改没有保存，原提醒时间仍然有效”，并提供重试。
- Windows、macOS、Linux 共用同一时间计算和持久化规则；通知是否持续显示仍按各平台能力降级，不改变两个时点的计划语义。
- 系统时区或夏令时变化后按当地时间意图重新计算未来时点，不补发已经过去的同日时点。

#### 7.10.5 非目标

- v0.7.0 不提供三个及以上每日时点、按星期分别设置时间、节假日模板、日历同步或批量覆盖已有事项。
- 不改变强调、强制方案的间隔提醒语义，也不把双时点设置加入快速录入必填链路。
- 不在本版本实现甘特图；只读甘特图按已确认路线放入 v0.10.0。

#### 7.10.6 验收标准

1. 后台可以保存两个不同的默认时间，非法或相同时间无法覆盖原设置。
2. 新安装及 v0.6.x 升级用户只出现一次新版引导；引导时间步骤可以查看并修改默认到期时间及两个重复提醒时间。
3. 引导完成后只影响新事项；跳过、`Esc`、关闭和保存失败均不修改原设置，保存失败时仍可重试。
4. 无指定时间的新重复事项复制两个默认时点；明确指定时间的新事项仍每天只提醒一次。
5. 创建时间位于第一个时点前、两时点之间和第二个时点后时，下一提醒计算分别正确且不补发已过时点。
6. 修改后台默认值不改变已有事项；主动恢复默认后才更新该事项未来时点。
7. 完成、暂停、删除、一次性跨日和月度/年度完成本次后不再错误触发原周期时点。
8. 休眠、重启、跨午夜、月末、年末、夏令时、时区变化和时间回拨均不漏掉下一个有效时点，也不重复轰炸。
9. schema 迁移测试证明 v0.6.x 旧重复事项仍保持每天一次，升级前备份可恢复。
10. 快速录入窗口尺寸、焦点、IME 和一次提交路径不因该功能增加额外阻塞操作。

### 7.11 更新与重装的数据保留（v0.7.1）

> 实施状态：2026-09-02 已完成代码、自动检查、界面截图复核与 Windows 构建；Windows NSIS 覆盖更新/重装及 macOS/Linux 对应安装包的真实数据目录验收待完成。本版本是数据可靠性补丁，只恢复已经确认的“升级不丢数据”行为；自定义仓库和多来源自动归并仍放在 v0.8.0。

#### 7.11.1 目标与范围

- 覆盖更新、相同版本重装、应用安装目录变化和应用程序文件替换后，继续读取原来的用户数据目录，不因程序路径变化创建新的空库。

1. 启动更新后的版本时，先解析并记录预期数据位置，再检查数据库存在性、文件大小、schema 版本和基本一致性。
2. schema 迁移前创建 SQLite 一致性备份，备份包含数据库及恢复所需的关联状态；备份成功后才开始事务迁移。

5. 重装默认不删除用户数据。卸载若提供删除数据选项，必须默认不勾选，并明确写出将永久删除的范围；覆盖更新流程不得出现该选项。

#### 7.11.3 失败行为与验收标准

- 若更新后暂时无法打开原数据库，应用不得显示一个看似正常的空事项列表；应说明“原数据仍在，当前版本暂时无法读取”，并停止创建会与原库竞争的新数据源。

验收要求：

1. 使用 v0.7.0 创建包含七类事件、标签、提醒历史和自定义设置的样例库，覆盖安装 v0.7.1 后数量、关系、时间和未来提醒保持一致。

3. 数据库只读、损坏、磁盘空间不足、备份失败和 schema 版本过新时均停止破坏性写入，并能从原文件或一致性备份恢复。

### 7.12 本地数据仓库与安全归并（v0.8.0）

### 7.13 邮件提醒体系完善（v0.9.0）

> 实施状态：2026-09-05 已完成代码、数据迁移、自动检查与 Windows 构建，待统一验收。v0.5.0 已提供基础 SMTP 和标签路由；本版本不改写历史，而是完善提醒方案、通知渠道和投递策略的分层。

#### 7.13.1 分层模型

- **事件类型**说明事项如何随时间发生，例如今日必做、预警或年度。
- **提醒方案**说明何时触发，例如重复、强调、一次性、强制或自定义。
- **通知渠道**说明通过哪里送达，首版包括系统通知、应用置顶窗和 SMTP 邮件。
- **投递策略**说明某渠道何时参与，例如仅首次到期、每天第一次、每次计划提醒或每日摘要。

邮件是通知渠道，不新增第六种提醒方案。更换邮件渠道不得改变事项时间；更换提醒方案也不得静默启用邮件。

#### 7.13.2 产品规则

1. 邮件继续默认关闭，只有用户完成服务器配置、测试成功并明确启用后才允许后台联网。
2. 用户可按事件类型、单选类型或标签建立投递规则；多条规则命中同一地址和同一计划提醒时只发送一次。
3. 每条规则明确显示收件地址、命中条件、投递策略和最近结果。登录邮箱、账户找回邮箱与提醒收件地址相互独立。
4. 快速保存只写入本地事项和待投递任务，不等待网络；邮件发送失败不撤销事项，也不影响系统通知。
5. 失败重试有限、持久化且使用稳定幂等键。达到上限后进入“需要处理”，说明本地事项安全并提供重新测试、修改设置或重试投递。
6. 未登录也能使用本机 SMTP；本版本要求电脑和闪记在计划时间处于可运行状态，不承诺关机后由云端代发。
7. 密码或授权码继续只存放在操作系统安全存储；导出、日志、个人数据仓库和未来云同步均不得包含明文凭据。

#### 7.13.3 UI 与跨平台

- 实现前使用 `frontend-design` skill 形成投递路径草图、自检结论和截图复核；界面从用户视角使用“邮件提醒”“发送测试邮件”“等待重试”等文字，不展示 SMTP 内部错误或命令名。
- Windows、macOS、Linux 共用规则、队列和幂等语义；凭据存储不可用的平台不得退化为明文文件，应禁用邮件并说明如何修复系统安全存储。
- 设置页必须覆盖未配置、验证中、可用、验证失败、凭据失效和网络不可用状态。

#### 7.13.4 验收标准

1. 相同事件可组合任意已确认提醒方案与邮件渠道，切换任一维度不会误改另一维度。
2. 首次、每日一次、每个计划时点和摘要策略分别有固定时钟测试；多规则命中不会重复发信。
3. 断网、认证失败、服务器拒绝、重启和休眠恢复不会阻塞本地保存或制造邮件风暴。
4. 关闭邮件后无邮件联网请求；删除路由后未来任务停止，既有投递历史保留且不含正文和凭据。

#### 7.15.2 注册、登录与个人资料（账户与备份阶段）

1. 支持主邮箱注册和验证、邮箱加密码登录、邮箱验证码快捷登录、保持登录以及退出其他设备。
2. 密码支持长口令和 Unicode，不要求机械组合大小写、数字和符号；服务端拦截常见或已泄露密码，采用带盐的抗离线攻击哈希并限制连续失败尝试。
3. 个人资料包括昵称、头像、主邮箱、备用找回邮箱、云空间用量、账户安全状态和已绑定设备；邮箱默认不公开。
4. 头像支持 JPG、PNG、WebP，客户端裁剪为方形、限制尺寸并清除定位等元数据；删除后恢复昵称首字或默认头像。头像不占事项空间额度。
5. 登录邮箱、备用找回邮箱和邮件提醒收件地址是三个独立概念；修改任何一项不得静默修改另两项。
6. 用户可以主动开启验证器应用生成的一次性验证码作为第二步验证；启用前必须生成并确认保存恢复码。新设备、敏感资料修改和关闭第二步验证时重新验证，普通快速记录不重复打断。

#### 7.15.3 二次绑定与找回（账户与备份阶段）

- 支持备用邮箱、可信设备确认和一次性恢复码三类找回凭证；引导用户至少配置一种主邮箱之外的找回方式。
- 主邮箱可用时可以通过邮箱验证重置登录凭证；主邮箱不可用时，需要“备用邮箱 + 恢复码”或“备用邮箱 + 可信设备确认”。
- 已开启第二步验证的账户不能只凭一封找回邮件绕过第二步验证；需要恢复码、可信设备或另一项已绑定验证凭证。
- 修改主邮箱、绑定新找回方式、执行账户恢复或移除可信设备时，通知主邮箱、备用邮箱和其他可信设备；可疑会话可以一次性撤销。
- 不使用姓名、生日、联系人或安全问题找回账户。
- “恢复账户登录”与“解密旧云端数据”分开：旧数据还需要恢复码或一台持有数据密钥的可信设备。两者全部遗失时允许重新取得账户，但必须明确告知旧加密数据无法恢复。

#### 7.15.4 云空间额度（账户与备份阶段）

- 每个账户初始免费额度采用已确认的 **100 MB**；额度为服务端可配置产品参数，调整不得追溯删除已有数据。
- 用量计算包括事项、备注、类型、标签、提醒方案、历史版本、墓碑和用户生成的备份；头像、系统索引、同步协议元数据、安全审计记录和凭据不计入事项空间。
- 设置页显示已用、总量、等待上传数量和主要占用类型，不能用数据库文件物理大小制造用户无法解释的波动。
- 达到额度后，已上传内容保持可读和可导出；新修改留在本地并标记等待上传。本地记录和本地提醒继续工作，释放空间或扩容后自动恢复。
- 服务端不得因超额静默驱逐数据。用户删除云端内容时先进入可恢复阶段，墓碑继续参与多设备归并。

#### 7.15.5 云备份、注销与分阶段同步

- 账户与备份阶段 先提供端到端加密云备份、恢复、设备列表和完整导出；服务端只保存密文、必要索引和最小化投递元数据。
- 增量同步阶段 再提供多设备增量同步、同步游标、冲突副本、删除墓碑和跨设备邮件投递幂等；各设备继续以本地 SQLite 支持离线运行。
- 退出登录时用户选择“保留本机数据”或“清除本机云端副本”；清除前再次确认并验证本地未同步内容如何处理。
- 注销账户前提供完整导出。注销采用已确认的 **30 天撤销期**；期间停止新云端操作但允许撤销注销，期满后删除个人云空间和账户资料，并保留依法或为防滥用所必需的最小去标识记录。

#### 7.15.6 概念数据关系

```text
用户账户
└── 个人数据空间
    ├── 账户资料与找回绑定
    ├── 已授权设备与会话
    ├── 加密事项、类型、标签和提醒方案
    ├── 空间额度与备份版本
    └── 同步操作、冲突和删除墓碑（增量同步阶段）
```

账户 ID、设备 ID、数据空间 ID 和事项 ID 必须相互独立。事项不使用邮箱作为外键，用户更换邮箱不得迁移或重写业务数据。

#### 7.15.7 失败行为与跨平台

- 登录、上传、下载、解密或配额检查失败时，界面说明本机内容是否安全、哪些内容仍待同步以及下一步操作，不展示服务端堆栈、内部字段或密钥信息。
- Windows、macOS、Linux 共用账户、加密包和同步协议；系统凭据存储、后台运行和网络恢复由平台适配器实现。平台无法安全保存凭据时不得提供自动登录。
- 多设备冲突不得静默选择最后写入者覆盖全文；用户可以比较两个完整版本，保留一个或保留两份。
- 云端永远不成为快速保存和本地提醒的同步依赖；断网、服务维护、账户冻结或空间超额时本地功能仍可用。

#### 7.15.8 非目标与验收标准

账户与备份阶段 不包含团队共享、公开资料页、第三方社交登录、云端附件、付费方案、移动端或云端 AI 分类。空间扩容和商业化需另行 PRD 确认。

验收要求：

1. 未登录状态无账户网络请求且本地功能完整；登录不会覆盖或重复已有本地事项。
2. 注册、验证、登录、退出、头像、主邮箱修改、备用邮箱、恢复码、可信设备和注销撤销均覆盖成功、失败和安全通知路径。
3. 100 MB 临界值、超额、释放空间和服务端调整额度不会导致本地保存失败或云端静默丢失。
4. 没有恢复码或可信设备时，界面在可能导致旧数据不可恢复之前明确阻止或二次确认。
5. 30 天撤销期内可恢复账户；期满删除任务可验证、可审计且日志不包含事项正文。
6. 增量同步阶段 的多设备并发编辑、删除、离线重连、重装和邮件投递均通过冲突与幂等测试。

## 8. 核心用户流程

### 8.1 快速记录

1. 用户在任意应用按全局快捷键。
2. 悬浮输入框出现在当前活动屏幕并获得焦点。
3. 用户输入内容；系统可在输入框下方展示识别到的时间和分类标签。
4. 用户按 `Enter`。
5. 后端校验并在单个事务中写入事项、到期规则及操作事件。
6. 保存成功后给出短暂视觉反馈并隐藏窗口，将焦点归还原应用。
7. 若保存失败，窗口保持打开，原文不丢失，提供重试和复制文本。

### 8.2 到期与顺延

1. 调度器发现事项到期，生成唯一提醒事件并发送系统通知。
2. 用户选择完成：事项进入 `DONE`，停止后续提醒。
3. 用户忽略且事项为默认下班时间：跨过该工作日后，系统将其顺延至下一工作日下班时间。
4. 用户忽略且事项为“今日必做”：不顺延，在后台计算下一次间隔提醒，并持续到完成或明确暂停。
5. 管理页显示“已自动顺延 1 次”或“今日必做 · 持续提醒中”，并允许用户修改策略。

### 8.3 休眠恢复

1. 应用收到恢复事件或检测到时钟跳变。
2. 后端重新读取所有未完成事项并重建调度计划。
3. 对休眠期间错过的事项生成一次汇总或单次补发通知。
4. 已发送的提醒事件不重复触发。

## 9. 信息架构与界面草案

### 9.1 快速录入窗

```text
┌────────────────────────────────────────────┐
│  写下要记的事…                             │
│                                            │
│  [默认：今天 18:00]  [事件类型]  [今日必做] │
│  Enter 保存 · Shift+Enter 换行 · Esc 关闭  │
└────────────────────────────────────────────┘
```

要求：无标题栏或使用极简标题栏；支持拖动；多显示器和不同缩放比例下不越界；浅色、深色和高对比度主题可用。

### 9.2 管理窗口

- 左侧：全部、今天、逾期、已完成、回收站。
- 中间：可排序事项列表，突出到期时间与顺延次数。
- 右侧或弹层：标题、备注、分类、标签、时间、提醒和历史。
- 顶部：搜索、新建、批量操作入口。

## 10. 数据模型（概念级）

### 10.1 `items`

| 字段 | 含义 |
| --- | --- |
| `id` | UUID/ULID，跨导入导出保持稳定 |
| `title` | 快速录入原文的首行或完整短文本 |
| `notes` | 可选长备注 |
| `status` | `OPEN` / `DONE` / `ARCHIVED` / `DELETED` |
| `event_kind` | 可空；固定七种时间性质，空值表示待选择事件类型 |
| `category_id` | 可空；用户自定义的单选类型，空值显示为未分类 |
| `due_at` | 当前计算出的到期时刻 |
| `due_local_date` / `due_local_time` | 本地下班时间等墙上时间意图 |
| `due_source` | `EXPLICIT` / `DEFAULT_EOD` / `ROLLED_OVER` |
| `rollover_policy` | `NONE` / `NEXT_WORKDAY_EOD` / `DAILY` |
| `rollover_count` | 自动顺延次数 |
| `completion_policy` | `NORMAL` / `MUST_COMPLETE_TODAY` |
| `repeat_interval_minutes` | 今日必做事项的重复提醒间隔；为空时读取后台默认设置 |
| `reminder_plan` | 重复、强调、一次性、强制或自定义预设 |
| `next_reminder_at` | 调度器计算出的下一次提醒时刻 |
| `bypass_app_quiet_hours` | 是否允许突破应用内勿扰时段，不代表能绕过系统勿扰 |
| `created_at` / `updated_at` / `completed_at` | UTC 审计时间 |
| `revision` | 乐观并发与导入合并使用 |

### 10.2 其他实体

- `categories`：用户自定义单选类型的名称、颜色、排序、归档状态。
- `tags` / `item_tags`：多标签关系。
- `reminder_events`：计划时间、实际发送时间、幂等键、结果。
- `item_events`：创建、编辑、顺延、完成、恢复等审计事件。
- `settings`：快捷键、工作周、下班时间、静默时段、数据目录等。
- `drafts`：尚未提交的快速输入草稿。
- 后续云功能的规划实体：`accounts`（账户资料）、`recovery_bindings`（备用找回方式）、`devices`（可信设备）、`vaults`（个人数据空间）、`cloud_quotas`（额度）以及 `sync_operations` / `conflicts` / `tombstones`（后续增量同步阶段）。这些实体不以邮箱作为业务主键。

数据库迁移必须带版本号。应用升级前自动创建可恢复备份，迁移失败时不得继续写入未知结构。

## 11. 推荐技术方案

### 11.1 技术栈

- 桌面壳：Tauri 2。
- 核心服务：Rust，负责快捷键事件、单实例、窗口控制、SQLite 访问、时间计算、调度和导入导出。
- UI：TypeScript + Svelte（避免引入大型 UI 套件，优先原生 CSS 与少量无障碍组件）。
- 本地数据：SQLite；所有写操作通过 Rust 命令进入单一数据访问层。
- 通知与系统集成：使用 Tauri 官方或经过审查的插件，并在权限配置中采用最小能力集。

选择理由：Tauri 使用系统 WebView，通常比打包完整浏览器内核的方案更适合轻量桌面工具；Rust 适合实现稳定的本地调度、数据层与平台适配。Tauri 2 官方提供桌面端全局快捷键能力，并支持 Windows、macOS、Linux 分发形式。

### 11.2 模块边界

```text
UI / Quick Capture Window
          │ typed commands/events
          ▼
Application Services
  ├─ CaptureService
  ├─ ItemService
  ├─ ReminderScheduler
  ├─ RolloverService
  └─ ImportExportService
          │
          ▼
Domain Rules + Repository Interfaces
          │
          ├─ SQLiteRepository
          ├─ SystemClock / TimeZone
          ├─ NotificationAdapter
          ├─ GlobalShortcutAdapter
          └─ Window / Autostart / Tray Adapters
```

时间计算不得散落在 UI 组件或 SQL 查询中。所有“下班时间”“下一工作日”和“是否应补发”判断集中在可注入时钟的领域服务中，以便对日期边界、时区和休眠场景做确定性测试。

### 11.3 调度策略

- SQLite 是提醒计划的事实来源，内存定时器只是加速器。
- 启动、恢复、系统时间/时区变化和事项修改时，重新计算最近一批提醒。
- 同时设置短周期健康检查，修复操作系统漏发的恢复事件。
- 发送前写入或原子领取唯一提醒事件，确保多线程或意外多开时仍幂等。
- 通知发送失败记录原因并退避重试；不能因此阻塞事项编辑或保存。

### 11.4 分发与便携性

- Windows：优先提供签名安装包；验证后再提供 ZIP 便携版。系统 WebView 缺失时给出可理解的安装提示。
- macOS：提供签名并公证的 DMG/App；全局快捷键、通知和开机启动按系统要求请求权限。
- Linux：优先 AppImage，同时评估 deb/rpm；在 Wayland、X11 及常见桌面环境分别验证全局快捷键与托盘差异。
- 用户数据与程序文件分离；便携模式仅在显式标记存在时将数据写入程序旁的 `data/`，普通安装遵循系统应用数据目录。

#### 11.4.1 v0.10.1 Windows 安装向导中文修复

> 确认状态：2026-09-06 用户确认继续修复。此补丁只补齐安装与卸载的中文，不扩展安装功能。

- 目标与范围：面向中文 Windows 用户，首次安装、覆盖更新、重装、卸载及安装器自身的异常提示统一使用简体中文；直接进入向导，不增加语言选择步骤。
- 非目标：不更换向导布局，不改变安装权限、程序标识、数据目录或卸载保留数据的默认行为；不新增联网能力、签名或自动更新。
- 失败行为：应用仍在运行、运行组件下载或安装失败、卸载失败时，中文提示说明阻碍和下一步；不在主提示中展示内部错误码，不承诺失败操作已回滚。
- 跨平台差异：本次仅修改 Windows NSIS 安装器；Windows 系统安全提示及第三方运行组件自身界面由系统或组件决定语言。macOS/Linux 分发行为不变，便携 ZIP 没有安装向导。

### 11.5 v0.5.1 跨平台测试分发

> 确认状态：2026-08-31 已确认。此版本只建立可复现的测试分发闭环，不将未经真实设备验证的平台描述为正式支持。

目标：让测试用户可以从同一个已确认版本取得 Windows、macOS 和 Linux 安装包，并能够核对文件完整性和了解平台限制。

范围：

- 使用受托管的 Windows、macOS、Linux 构建环境，从同一 Git 提交和应用版本生成安装包。
- Windows x64 生成 NSIS 安装包和 ZIP 便携包；macOS 生成兼容 Apple Silicon 与 Intel 的通用 DMG；Linux x64 生成 AppImage 和 DEB。
- macOS 测试包在没有 Apple Developer 凭据时使用临时签名，发布说明必须明确首次打开可能需要用户在系统“隐私与安全性”中允许。
- 每次测试发布生成 `SHA256SUMS.txt`，并将安装包、校验文件和平台说明放在同一草稿预发布中。
- 流水线只使用仓库源码和依赖构建，不读取或上传本地事项、数据库、导出文件、凭据与日志。

非目标：

- v0.5.1 不加入自动更新、应用商店发布、账号、遥测或新的联网产品功能。
- 未提供 Apple Developer 证书时不承诺 macOS 公证；未提供 Windows 代码签名证书时不承诺消除 SmartScreen 的未知发布者提示。
- 自动构建成功不替代 macOS、Linux 真实设备上的快捷键、托盘、通知、休眠恢复和开机启动验收。

失败与恢复：

- 任一平台构建或校验失败时，不发布该平台产物，也不得复用旧版本文件冒充本次构建。
- 发布任务必须保留可定位到提交的构建记录；凭据缺失只允许降级为已声明的测试签名，不能把未签名或未公证状态隐藏起来。
- 校验文件生成失败时整次发布失败，避免用户取得无法核验来源的零散文件。

跨平台差异：

- Windows 测试包可运行，但未配置发布者证书时系统可能显示未知发布者提示。
- macOS 通用 DMG 覆盖 Apple Silicon 与 Intel；临时签名包仍可能被 Gatekeeper 拦截，需要用户手动允许。
- Linux AppImage 适合免安装测试，DEB 面向 Debian/Ubuntu；Wayland、X11 和不同通知服务的行为分别记录，不假定完全一致。

验收标准：

1. 三个平台的产物版本、Git 提交和发布标签一致，文件名可以辨认平台、架构和格式。
2. Windows 生成 NSIS 与便携 ZIP，macOS 生成通用 DMG，Linux 生成 AppImage 与 DEB；全部文件写入同一 `SHA256SUMS.txt`。
3. 流水线先执行前端类型检查、测试、生产构建以及 Rust 格式、静态检查和测试；任何一项失败都不发布。
4. 发布默认保持“草稿 + 预发布”，只有真实设备完成安装、启动、快捷键、保存、通知、托盘和开机启动检查后才能转为正式发布。
5. 发布说明明确签名状态、支持范围、已知降级、数据目录和卸载不删除用户数据的规则。

## 12. 非功能需求

### 12.1 性能目标

以下数值是 MVP 验收目标，需在发布基线设备上实测并记录：

| 指标 | 目标 |
| --- | --- |
| 后台已运行时，快捷键到输入框可输入 | P95 ≤ 200 ms |
| 按 Enter 到确认保存 | P95 ≤ 100 ms |
| 冷启动到后台可用 | P95 ≤ 1.5 s |
| 空闲 CPU | 5 分钟平均 < 0.5% 单核 |
| 空闲内存 | 典型值 ≤ 80 MB；各平台单独记录 |
| 安装包体积 | 目标 ≤ 25 MB，不含系统 WebView 运行时 |
| 事项容量 | 10 万条事项下，常用列表和搜索 P95 ≤ 300 ms |

### 12.2 可靠性

- 本地保存成功率目标 ≥ 99.99%，不含磁盘满、权限丢失等明确外部错误。
- 崩溃后已确认保存的数据不得丢失；未提交草稿可恢复。
- 时间规则测试覆盖月末、年末、闰日、夏令时切换、时区变化和系统时间回拨。
- 数据库采用事务、外键约束和适当的同步策略；应用不得静默忽略写入错误。

### 12.3 可用性与无障碍

- 快速录入主路径可全键盘完成。
- 支持中文输入法组合态，不能把输入法确认键误判为提交。
- 控件有可访问名称、可见焦点，颜色不作为唯一状态信号。
- 支持系统缩放、减少动态效果、高对比度和屏幕阅读器基础操作。

### 12.4 隐私与安全

- 默认不联网，不采集事项正文、键盘内容或使用行为。
- 崩溃日志默认移除事项内容和本地路径；上传前由用户预览并同意。
- 数据导出是明确用户动作，导出文件提醒用户可能包含敏感信息。
- 快捷键只通过受限系统 API 注册，不实现全局按键日志。
- 若未来接入云端分类或同步，必须单独提供数据范围、加密、删除和退出机制。
- 机密令牌不得存 SQLite 明文，使用系统凭据存储。

## 13. 异常与边界场景

必须有明确行为的场景包括：

- 快捷键被其他应用占用或注册中途失效。
- 当前为锁屏、安全桌面、全屏游戏或系统保留快捷键环境。
- 中文输入法正在候选态时按 Enter。
- 多显示器断开、负坐标、DPI/缩放不同、活动窗口识别失败。
- 通知权限被拒、系统勿扰模式开启或桌面环境没有通知服务。
- 今日必做事项持续提醒期间修改间隔、暂停、完成或跨过午夜。
- 应用在到期前退出、到期时休眠、恢复时时区已改变。
- 系统时间向前或向后跳变。
- 数据库被占用、损坏、只读、磁盘已满或便携介质被拔出。
- 导入重复事项、旧版本数据和部分损坏文件。
- 程序重复启动或升级过程中发生崩溃。

## 14. 数据与成功指标

MVP 不要求远程埋点。若用户自愿开启匿名统计，只允许采集不含正文的聚合指标。

建议指标：

- 唤起成功率、保存成功率、通知调度成功率。
- 快捷键到可输入的 P50/P95 延迟。
- 快速录入后 10 秒内退出率，用于发现误唤起。
- 默认下班时间事项的完成率、平均顺延次数。
- 快捷键冲突率、通知权限拒绝率和崩溃率。

产品成功的首要判断：一周活跃用户中，至少 60% 的新增事项来自全局快速录入；快速录入保存成功率 ≥ 99.9%。该目标需在有足够样本后复核，不作为首轮内测的硬门槛。

## 15. MVP 验收清单

发布 MVP 前至少完成以下端到端验收：

1. 三个平台可安装/运行、注册快捷键、唤起输入框、保存并收到通知。
2. 输入框在当前屏幕出现并自动聚焦，保存后焦点回到原应用。
3. 输入法组合态、换行、取消、重复唤起均无误提交或丢字。
4. 未设时间事项按工作日和下班时间正确计算；下班后创建不会立即逾期。
5. 未完成默认事项只顺延一次到下一工作日，且保留历史。
6. 显式设定时间的事项默认不自动顺延。
7. 今日必做事项到期后按后台配置间隔持续提醒，下班和跨午夜后不自动顺延；完成或暂停后不再重复提醒。
8. 持续提醒在休眠、退出、重启、间隔调整和时间跳变后可恢复，并且不补发一串历史通知或重复轰炸。
9. 快捷键冲突、通知拒绝、磁盘满等失败有可行动提示，内容不丢失。
10. JSON 完整导出后，可在空数据库中恢复相同事项、分类、设置和历史。
11. 10 万条测试数据下满足列表、搜索和内存目标，空闲 CPU 无异常唤醒。
12. 应用不主动访问网络，除非用户手动检查更新或启用未来的网络功能。
13. 安装、升级、卸载和便携模式不会意外删除用户数据。

## 16. 发布阶段建议

### Phase 0：技术验证（1–2 周）

- 三平台全局快捷键、置前聚焦、托盘、通知和开机启动能力验证。
- 重点测试 macOS 权限、Linux Wayland/X11 差异和 Windows WebView 依赖。
- 使用临时 SQLite 完成“提交后落盘、重启后提醒”的最小闭环。
- 输出技术风险清单和实测延迟，不做完整界面。

### Phase 1：MVP（预计 4–6 周，取决于三平台验证结果）

- P0 快速录入、管理、分类、默认到期、顺延、通知、托盘、设置和备份。
- Windows 优先完成日常开发验证，macOS/Linux 通过 CI 和真实设备发布门禁。
- 小范围内测，重点收集误唤起、漏提醒和时间语义问题。

### Phase 1.1：稳定与效率

- P1 自然语言时间、本地规则分类、批量操作、历史、勿扰、提前提醒和更新。
- 评估双击单个修饰键的可行性；只有在不扩大键盘监听范围且误触可控时发布。

### Phase 2：生态扩展

- 按第 7.15 节先提供账户与有限云空间，再开放可选端到端加密同步；未登录状态继续完整使用本地功能。
- 后续再独立评审系统日历、移动端收集入口、本地模型分类和插件接口。
- 每项网络能力独立授权，不改变离线核心的可用性。

## 17. 主要风险与缓解

| 风险 | 影响 | 缓解方案 |
| --- | --- | --- |
| 单键双击需要底层键盘钩子 | 权限敏感、误触、跨平台不一致 | MVP 使用组合键；单键双击做隔离的平台适配器和显式开关 |
| Linux 桌面环境碎片化 | 全局快捷键、托盘、通知行为不同 | 建立 Wayland/X11 支持矩阵，无法支持时清楚降级 |
| 休眠和系统时间变化 | 漏提醒或重复提醒 | 持久化计划、恢复后重建、提醒幂等键、可注入时钟测试 |
| 自动顺延掩盖长期积压 | 用户误以为事项是新任务 | 展示原始到期日和顺延次数，提供“停止顺延”与逾期视图 |
| 快速记录未选事件类型 | 事项时间语义待完善 | 保持可见的待选状态、单击设为普通、合并提示，不阻断保存 |
| 便携介质断开 | 数据写入失败或损坏 | 原子写入、WAL/事务策略评估、错误时保留草稿、提供备份 |
| 应用轻量与功能扩张冲突 | 资源占用和维护成本上升 | 以性能预算和非目标约束每个新依赖、网络服务和后台任务 |
| 账户找回成为数据解密后门 | 私密事项被未授权恢复 | 登录找回与数据密钥恢复分离，要求恢复码或可信设备并通知全部已绑定渠道 |
| 云空间超额或服务不可用 | 用户误以为新事项已上传 | 本地先保存、显示等待同步数量、云端不静默驱逐、恢复后幂等续传 |

## 18. 待产品决策

以下问题不会阻塞技术验证，但应在 MVP 界面定稿前确认：

1. 产品正式名称与图标方向。
2. “下一天”是否严格指下一自然日，还是默认按下一工作日；本稿采用下一工作日。
3. 首次启动是否直接采用建议值 18:00，还是强制用户先确认自己的默认时间；无论采用哪种方式，后续均可在后台设置中修改。
4. 自动顺延发生在午夜、原到期时间之后，还是次日首次启动时；本稿采用“逻辑上跨日即生效，实际在后台或下次启动执行”。
5. 显式设置时间的逾期事项是否也允许默认顺延；本稿默认不顺延。
6. 快速录入是否支持多行；本稿支持 `Shift+Enter` 多行。
7. 首发平台是否 Windows 优先，还是必须三平台同日发布。
8. 是否需要首版自然语言时间解析；本稿将其列为 P1，MVP 提供显式快捷时间选择。
9. 便携模式是否必须覆盖 macOS；本稿优先 Windows/Linux，macOS 遵循应用包和系统数据目录习惯。

## 19. 参考依据

- [Tauri 2 Global Shortcut](https://v2.tauri.app/plugin/global-shortcut/)：官方插件支持注册全局快捷键，且快捷键被占用时可能无法触发，因此产品必须检测冲突并提供重设入口。

- [OpenAI Docs：Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)：项目根目录说明适合作为仓库级协作约束，并可在子目录按作用域覆盖。
- [SQLite Over a Network](https://sqlite.org/useovernet.html) 与 [SQLite WAL](https://sqlite.org/wal.html)：正在写入的 SQLite 数据库不直接放入网络或同步目录；本产品使用本地运行库与经过校验的数据包归并。
- [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)：账户凭证、恢复码、多种找回方式和恢复通知的安全依据。
