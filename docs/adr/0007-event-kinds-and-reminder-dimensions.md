# ADR-0007：固定事件类型与提醒维度拆分

- 状态：已接受
- 日期：2026-09-01
- 关联版本：v0.6.0

## 背景

v0.5.x 将可编辑“工作/个人”分类、今日必做执行要求、重复间隔和通知展示方式分散在多个字段与全局开关中。新增普通、一次性、预警、持续、月度和年度事件后，如果继续把事件生命周期、触发频次和持续通知放在同一枚举中，会产生无法解释的组合，例如“持续事件每三天强制提醒”或“预警事件到目标时间后如何接管”。

快速录入还必须允许用户先可靠保存、稍后补选事件类型，因此“未选择事件类型”需要存在，但不能重新成为用户可见的“收件箱”类型。

## 决策

1. 固定七种事件类型：普通、一次性、今日必做、预警、持续、月度、年度。“重要”作为跨事件类型标记。
2. 事项分类采用三层模型：
   - 事件类型：固定单选，表达时间性质、生命周期和必需时间字段；
   - 类型：用户自定义单选，表达工作、个人等事项性质；
   - 标签：用户自定义彩色多选，表达项目、客户等可复用内容特征。
3. 将提醒领域语义拆为三个正交维度：
   - 事件类型：生命周期、必需时间字段和周期实例语义；
   - 时间规则：一次、每天、间隔、日历周期、预警窗口或自定义阶段；
   - 通知强度：标准、强调或持续。
4. 用户界面仍提供“重复、强调、一次性、强制、自定义”五个提醒方案，但它们是上述时间规则和通知强度的预设，不作为唯一事实字段。
5. 未选择事件类型使用可空 `event_kind` 表达内部待处理状态；它不出现在事件类型列表。`category_id` 继续表达可空的单选类型，`item_tags` 继续表达多选标签。
6. 事件类型转换在单个事务中更新未来计划并写入审计事件，同时保留单选类型和标签。历史到期点、已发送提醒和用户原文不可改写；逾期转换需要未来时间时建立新计划。
7. schema v6 以加列和新表迁移为主，不删除 v5 的旧表或列。旧 `categories`、`tags` 和它们的事项关系分别原样保留，不相互复制；旧提醒计划先保持原行为，以便回滚和核对。

## 结果

### 正面影响

- 可以表达“持续 + 每三天 + 强制显示”等组合，而不增加互相冲突的事件类型。
- 同一“工作”类型可横跨七种事件类型，转换时不需要重复创建或丢失分类。
- 普通与一次性的默认行为清楚，但用户仍可在后台覆盖提醒方案。
- 快速录入无需增加必填步骤，后台能持续提示待补全类型。
- 旧数据能够增量迁移并保留恢复路径。

### 代价与风险

- 调度器需要根据事件类型和提醒方案计算下一触发点，测试矩阵增大。
- 月/年日历周期、时区变化和休眠恢复必须使用领域函数集中计算，不能依赖固定秒数。
- Windows 可以在通知中直接处理分类，macOS/Linux 需要应用内降级入口。

## 被否决的方案

### 将“重要”保留为第八种事件

重要程度与生命周期无关，会阻止“重要的预警/年度事件”等自然组合，并使类型数量与已确认的七类冲突。

### 将“强制”作为时间频率

强制描述的是可见性而不是时间，无法表达“每三天强制显示”，也容易与持续事件和强调间隔重叠。

### 自动把所有未选类型记录设为普通

虽然操作更少，但会丢失用户希望稍后确认事件语义的信息。本方案保留无阻塞保存，同时提供单击“设为普通”和合并待分类提示。

### 把工作、个人等全部改为标签

多选标签无法稳定回答“事项主要属于哪种性质”，会让统计、默认视图和数据迁移产生歧义。因此保留单选“类型”，标签只承担多选补充语义。
