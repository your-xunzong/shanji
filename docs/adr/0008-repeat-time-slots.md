# ADR-0008：重复提醒采用事项级当地时间快照

- 状态：已接受
- 日期：2026-09-01
- 关联版本：v0.7.0

## 背景

“重复”提醒需要支持每天两个默认时点，同时保留用户明确指定一个时间后每天只提醒一次的行为。后台默认时间未来可以修改，但既有事项不能因此被静默改期。调度还必须正确处理休眠恢复、跨午夜、时区变化和系统时间回拨，且 v0.6.x 已有重复事项升级后不得自动增加提醒次数。

## 决策

1. 后台设置保存两个有序、互不相同的当地时间，默认值为 `10:00` 和 `17:00`。
2. 每个重复事项保存时间来源和一至两个当地时间快照：
   - `DEFAULT` 表示创建、转换或主动恢复默认时复制了当时的后台默认值；
   - `SPECIFIED` 表示用户明确指定一个每天提醒时间。
3. 事项调度只读取事项自身的时间快照，不在每次计算时动态引用后台默认设置。后台设置变更只作为之后新建、转换或恢复默认的种子。
4. schema v7 使用明确列保存默认时间、来源和两个时间槽，不使用不透明 JSON；当地时间意图与 UTC 审计时间继续分开保存。
5. v0.6.x 已有重复事项迁移为 `SPECIFIED`，第一个时间取原 `due_local_time`，第二个时间为空；其他事项保留原计划。
6. 调度器集中寻找当前当地日期之后的第一个有效时间槽。休眠或退出期间错过多个槽位时只领取当前一条到期提醒，随后直接计算下一个未来槽位。
7. 每个事项、当地日期和时间槽继续形成稳定幂等边界；迁移、时间回拨和多开不得生成同一槽位的重复投递。

## 结果

### 正面影响

- 已有事项不会因全局默认设置变化而意外改变提醒时间。
- v0.6.x 数据可以无损迁移，升级前后仍保持每天一次。
- 两个时间是结构化字段，便于校验、查询、导出和后续迁移。
- Windows、macOS、Linux 共用同一领域计算，平台通知能力不影响计划语义。

### 代价与风险

- 设置和事项各自保存时间，需要在“恢复默认”操作中显式复制并提示结果。
- 调度测试需要覆盖两个槽位、生命周期边界、时区变化和错过多次后的单次补发。
- 首次引导版本需要提升，已完成旧引导的用户会看到一次新版时间设置说明。

## 被否决的方案

### 调度时始终读取当前全局默认值

这会让一次设置修改静默重排所有既有事项，与“设置只影响之后事项”的确认语义冲突，也难以审计提醒为何变化。

### 新增第六种“双时点”提醒方案

双时点只是“重复”方案的时间配置，不是新的生命周期或通知强度。新增方案会扩大前台选择成本，并与用户确认的五种提醒方案冲突。

### 使用 JSON 保存任意数量的时间

v0.7.0 明确只支持一至两个时点。JSON 会弱化约束、迁移和查询能力，同时为尚未确认的三个及以上时点提前引入复杂度。
