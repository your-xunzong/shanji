# ADR-0009：启动前数据连续性检查与副本迁移

- 状态：已接受
- 日期：2026-09-02
- 关联版本：v0.7.1

## 背景

SQLite 在打开不存在的目标路径时会立即创建新文件。若覆盖更新、重装或安装路径变化后目标位置解析异常，应用会继续进入一个看似正常的空事项列表，用户难以判断原数据仍在其他位置。现有 schema 升级虽然先创建一致性备份，但仍直接在当前库上逐级执行迁移；中途失败时原文件可能处于部分升级状态。

## 决策

1. 安装版始终使用由稳定应用标识 `com.shanji.desktop` 解析出的系统应用数据目录；程序安装目录和可执行文件位置不得参与安装版数据库定位。只有可执行文件旁存在显式 `portable.flag` 时才使用同目录 `data/shanji.db`。
2. 打开 SQLite 写连接前执行只读启动检查：确认目标是否存在、是否非空、schema 版本、SQLite 快速完整性、外键一致性、事项数量、设置、草稿和提醒历史摘要。
3. 目标不存在或没有事项、但在稳定应用目录、旧本地目录、程序目录、显式便携目录或既有备份目录发现经过校验的非空闪记数据库时，进入仅恢复启动模式。该模式只创建主窗口，不启动快捷键、快速录入、提醒窗口、调度器、托盘或邮件服务。
4. 目标损坏、只读、版本过新、备份失败、空间不足或迁移失败时停止写入并进入阻塞模式。界面说明原数据是否仍在、可执行动作和去敏诊断；不得创建竞争空库。
5. schema 迁移先使用 SQLite `VACUUM INTO` 创建并校验一致性备份，再生成同目录迁移副本。所有迁移只在副本执行；副本通过 schema、完整性和外键检查后，才在重启/关闭连接边界切换为当前库。
6. 恢复和迁移切换前，将原数据库及其 `-wal`、`-shm` 文件移动到 `backups` 中保留。若新副本切换失败，尽力把已移动文件回滚到原位置；不再直接删除旧 WAL/SHM。
7. v0.7.1 只扫描有限的应用已知位置并允许用户选择一份数据恢复，不递归扫描整台电脑，不自动合并两个非空库。多来源归并继续属于 v0.8.0。

## 影响

- 优点：空目标不会抢先成为事实来源；迁移失败不改写原库；恢复前后均存在可核对、可回退的文件。
- 代价：升级期间最多需要额外两份与数据库大小相近的空间；检查完整性和生成副本会增加启动升级时间，但不进入快速录入保存路径。
- Windows：安装目录变化不改变 `%APPDATA%` 下的稳定数据位置；NSIS 覆盖更新和重装需要真实验证。
- macOS/Linux：使用同一只读检查和副本迁移语义；系统应用数据目录、包覆盖更新和文件管理器打开行为需分别在真实设备验证。
- 隐私：启动摘要和诊断不包含事项正文、备注、路径以外的用户内容或 SMTP 凭据；完整路径只在本机默认收起区域显示。

## 被否决的方案

### 发现旧库后自动选择最新文件

文件更新时间不能证明哪份是用户希望保留的事实来源。自动覆盖还会把“恢复”误变成未确认的数据替换。

### 在原数据库上继续逐级迁移

事务只能保证单个迁移步骤，不能保证跨多个 schema 版本的整个升级保持原文件不变。使用副本迁移把失败边界放在最终切换之前。

### 直接在同步盘或旧程序目录打开数据库

这会重新引入程序目录权限、移动介质断开和网络文件系统锁语义。v0.7.1 只恢复到稳定本地运行库；个人仓库与安全归并由 v0.8.0 处理。
