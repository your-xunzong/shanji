# ADR-0015：GitHub 规范源、Gitee 发布镜像与客户端择快更新

- 状态：已接受；2026-11-04，v0.14.0

## 背景

v0.12.0 起更新器只信任 GitHub Release。部分网络环境访问 GitHub 较慢，用户希望每次发布同时上传 GitHub 与 Gitee，并由客户端根据本次网络响应选择更快的官方下载源。

Tauri 2 的静态多端点只在前一个端点返回非 2xx 时继续下一个端点，不能并发测量并选择低延迟源。Gitee Release 没有与 GitHub `/releases/latest/download/` 等价且稳定的匿名清单入口，因此正式镜像完成后由流水线把已校验的 Gitee `latest.json` 推到专用 `update` 分支。仅在 `tauri.conf.json` 中追加 URL 仍不能满足择快与一致性需求。

## 决策

1. GitHub `your-xunzong/shanji` 继续作为规范事实源、唯一构建源和完整附件历史；Gitee `wu_-ji/shanji` 作为只读发布镜像。
2. GitHub Actions 对每个正式标签只构建一次。相同产物、签名、说明与校验清单上传两个 Release；Gitee 不重新编译，也不持有第二把签名私钥。
3. 发布流程为 GitHub 草稿、Gitee 预发布镜像、双源校验、GitHub 正式发布、Gitee 转正式和最终只读复核。任一源未完成时不能宣称双源发布完成。
   Gitee Release 附件全部就绪后，最后更新 `update` 分支中的稳定清单，避免客户端看到半成品。
4. Gitee 访问令牌仅存 GitHub Actions 加密 Secret，并使用最小仓库权限。源码、日志、远端 URL、SQLite 和附件不得包含令牌。
5. Rust 更新适配器并发检查两个源。若版本不同选择较高稳定版；若版本相同且当前平台签名一致，选择有效清单响应更快的源；同版本签名不一致时拒绝镜像并使用 GitHub。
6. 下载失败最多从同版本、同签名的备用源重新开始一次。两个源继续使用编译进应用的同一 Minisign 公钥，签名验证不可关闭。
7. 仅允许精确的 GitHub/Gitee Release HTTPS 主机、仓库路径、版本标签和附件名。前端只展示状态并发起命令，不直接抓取、验证或安装更新。
8. 自动检查默认关闭。由于新增 Gitee 网络访问，旧的 GitHub 授权不静默扩权；升级后首次自动检查前重新确认双源访问。
9. Gitee 单附件发布前强制小于 100MB。镜像保留最近 5 个稳定版本的二进制附件，更旧版本保留 Git 历史、标签和说明，完整附件历史由 GitHub 保存。

## 影响

- 新增 Rust 侧待更新状态、并发源探测、下载进度通道和一次备用源切换；现有 JS updater 调用迁移为应用命令。
- 网络仍不进入快速录入、事项保存或提醒调度路径，不增加常驻服务和高频轮询。
- Gitee API 或附件服务故障不会阻塞 GitHub 更新；GitHub 故障时 Gitee 可独立完成签名更新。
- 发布流程需要 Gitee Secret、附件容量检查、双源哈希/签名比较和幂等补齐。

## 放弃的方案

### 只在 Tauri 配置中追加第二个端点

端点按顺序失败回退，不能按延迟选择；第一个端点返回有效但较慢时不会尝试第二个。

### 两个平台分别构建

会产生不同字节和签名，难以证明两源同版一致，也增加供应链和维护风险。

### 自建更新服务器或 CDN

会引入新的长期在线服务、凭据、运维和隐私边界，不符合当前离线优先和依赖预算。

### 允许用户填写任意镜像地址

会扩大更新供应链和钓鱼面，破坏精确来源白名单，首版不采用。
