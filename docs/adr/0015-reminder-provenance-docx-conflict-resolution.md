# ADR-0015：提醒来源、DOCX 模板与仓库冲突解决

- 状态：已接受
- 日期：2026-09-15
- 关联版本：v0.13.3

## 背景

事项只保存最终提醒方案时，系统无法解释该方案来自事件类型默认、重要默认还是用户单独覆盖。个人仓库已有保守冲突副本，但缺少解决结果的跨设备传播。月度和季度小结需要保留用户提供的 Word 格式，同时不能把大型办公运行时或网络服务带入常驻应用。

## 决策

1. 事项持久化提醒方案来源。既有事项迁移为“旧数据保留”；以后只有切换事件类型/重要状态、创建事项或用户点击“恢复默认”才重新匹配，用户手动选择则标记为单独设置。
2. “重要”默认方案保存于应用设置并优先于事件类型默认；它不改变事件类型、类型、标签或用户原文。
3. Word 小结采用用户 `.docx` 作为 ZIP/OOXML 模板。Rust 只处理正文 `word/document.xml` 中受支持的文本占位符和表格模板行，复制已有 OOXML 以保留格式；模板原文件只读，输出临时写入并重新打开校验后原子替换。
4. 首版 DOCX 不解释宏、域、外部链接、页眉页脚、文本框或 SmartArt 占位符。用户文字按 XML 文本转义，生成不联网、不执行模板内容。
5. 仓库完全重复以来源修订和规范化业务内容摘要共同证明。自动处理只把冗余记录标记为已合并并停止提醒，不做不可恢复删除。
6. 差异冲突保存稳定的两侧修订摘要和解决指纹。选择结果与来源映射进入仓库数据包，其他设备看到同一对修订时复用结果，不再生成冲突副本。
7. 恢复已完成事项沿用同一稳定事项 ID，写入新的修订和审计事件；只计算未来提醒，不从完成期间补发历史触发点。

## 依赖与体积

- 直接使用依赖树中已有的 `quick-xml` 与 `zip` 作为小型本地 OOXML 处理依赖，不引入 Office、LibreOffice、Node.js、Python 或常驻服务到生产应用。
- `quick-xml` 为 MIT 许可；`zip` 为 MIT 许可。两者跨 Windows、macOS、Linux 使用纯本地文件接口，不新增系统权限或网络能力。
- 开发与验收可以使用工作区提供的 LibreOffice 渲染器检查生成结果，但它不是应用运行时依赖，也不进入发布包。

## 影响

- SQLite schema 升级到 v12，需要迁移备份、失败恢复和旧数据来源保守标记。
- DOCX 模板兼容范围明确但有限；复杂模板需在收到实际文件后逐页验证。
- 已合并重复项仍保留来源和审计，占用少量数据库空间，换取可恢复性和跨设备一致性。
- 解决指纹只阻止同一对修订重复冲突；后续真实双向修改仍会产生新冲突。

## 被否决的方案

### 按标题或更新时间自动去重

标题不是稳定身份，设备时间会漂移，自动覆盖可能丢失备注、时间和完成状态。

### 直接修改用户模板

原地写入会在中断或模板不兼容时损坏唯一模板，因此只读模板并生成新文件。

### 生产应用调用 Word 或 LibreOffice

这会扩大包体、平台差异和外部进程故障面，不符合轻量、离线和三平台技术基线。

### 修改默认值时批量更新既有事项

无法区分历史默认和用户意图，会静默改变已排定提醒，因此只影响之后的明确动作。
